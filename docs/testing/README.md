# Testing docs

## Catalog merging

`docs/testing/automated_test_catalog.md` is generated by `scripts/generate-automated-test-catalog.ts` from the tracked test-file tree. It is gated by `npm run validate:test-catalog` (`generate-automated-test-catalog.ts --check`), which runs in CI on every PR.

`src/shared/capability_manifest.json` carries the identical mechanism: it is generated by `scripts/generate-capability-manifest.ts` and gated by `npm run validate:capability-manifest`.

Both files are declared **generated artifact, union-merge** in `.gitattributes`:

```
docs/testing/automated_test_catalog.md merge=union
src/shared/capability_manifest.json merge=union
```

Two branches that each independently add tests (or MCP tools) regenerate these files with the same deterministic ordering rules but different content. Without `merge=union`, merging such branches produces a git conflict on the generated file even though the underlying code changes don't overlap. With `merge=union`, git resolves the file automatically by unioning both sides' lines — no manual conflict resolution needed. This is expected, silent auto-resolution, not a bug.

Union-merge does not guarantee canonical ordering. The next `npm run generate:test-catalog` (or `npm run generate:capability-manifest`) run restores it. The `--check` gates already force this regenerate-and-verify step on every PR, so staleness — whether from a solo edit or a post-union-merge canonicalization gap — is always caught in CI:

```
❌ automated_test_catalog.md is out of date with tracked test files.
  Run: npm run generate:test-catalog
  Then commit the result and push.
```

```
❌ capability_manifest.json is out of date with tracked capabilities.
  Run: npm run generate:capability-manifest
  Then commit the result and push.
```

Run the named command, commit the regenerated file, and push.

### `openapi_types.ts` is excluded

`src/shared/openapi_types.ts` is explicitly **excluded** from `merge=union`. Unlike the test catalog and capability manifest, it is derived from a human-edited source (`openapi.yaml`), not from tree shape. Two branches that both hand-edit overlapping schema regions represent a genuine semantic conflict — a union merge could interleave incompatible generated TypeScript type blocks into invalid code. That file keeps standard merge behavior; conflicts there require manual resolution.

See the follow-up audit: [#2037](https://github.com/markmhendrickson/neotoma/issues/2037) — Audit openapi_types.ts conflict handling (excluded from generated-artifact union-merge — source-driven, not tree-shape-driven).
