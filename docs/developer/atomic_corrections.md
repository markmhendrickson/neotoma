# Atomic corrections across entities

`POST /corrections/transaction` (`correct_transaction` over MCP) applies a bounded set of ordinary correction observations in one existing database transaction. The CLI uses `neotoma request --operation correctTransaction --body '<json>'`. It is additive; existing single-entity correction behavior is unchanged.

Each of 1–50 unique targets supplies `entity_id`, actual `entity_type`, `expected_observation_count`, `expected_snapshot` fields and 1–50 unique `{field,value}` changes. Every changed field must be declared by the target's active schema. Read the current scoped snapshots immediately before constructing the transaction. The count catches concurrent writes even when timestamps coincide; expected fields additionally identify the state the caller reviewed.

The server authenticates the graph, applies the existing agent correction capability policy, and checks all targets inside the database transaction. A missing/cross-graph target, stale precondition, invalid field, failed write or correction that does not win the reducer rolls back all observations and snapshots. Existing observation/entity notifications are buffered until commit; a rolled-back attempt emits none.

The required `idempotency_key` belongs to the authenticated graph and complete canonical request. An exact retry returns `status: replayed` without new writes or notifications; changed payload with the same key fails. Receipts reuse the committed correction observations and their canonical hash. Responses contain current scoped snapshots, including on replay, rather than a frozen historical response. After an uncertain network response, retry the identical payload/key before deciding whether to construct a new transition. Do not overwrite a conflict or escalate correction priority to force it to win.

This is a State Layer primitive. It does not interpret approvals, allocate application capacity, fetch external documents or certify human consent. The caller must derive its business transition and authorization from its own reviewed inputs, and include all affected entities in the transaction. The database commit cannot make an external document immutable; applications must verify external revisions through authorized APIs and retain their revision proof separately.

Validation uses isolated SQLite data: concurrent distinct transactions sharing one remaining resource permit only one winner; exact concurrent replays produce one commit; an injected second-write failure rolls back the first; reducer mismatch, scope violations and changed replay payloads fail without partial state. See `src/services/correction_transaction.test.ts` and the authenticated HTTP tenant matrix.

The committed `atomic_correction_transaction_recovery` eval scenario maps natural `correct_transaction` arguments through the existing replay harness to the isolated real HTTP route. It checks initial stale refusal, coordinated persistence, exact uncertain-response replay, changed-payload refusal and a stale final-capacity competitor, including every target's snapshot and observation count. Run `npm run eval:scenarios -- --scenario atomic_correction_transaction_recovery --provider stub`. Its cassette contains requests only, never canned results. Removing the precondition comparison makes nine of its eleven assertions fail. Post-commit event delivery is independently covered by the service tests: four events on the coordinated commit, none on rollback or exact replay. The scenario is deterministic replay coverage; it does not claim a live-model reasoning evaluation or simultaneous HTTP arrival.

`tests/cli/request_atomic_transaction.test.ts` invokes the built generic CLI operation against that same real isolated server with both natural `--body` and `--params` arguments. Each verifies commit, exact replay, changed-payload and stale refusals, followed by authoritative snapshot/count read-back. Pointing only the built operation mapping at a missing route makes both tests fail; restoring it returns both to green. No additional CLI implementation or transport is introduced.

## Native request validation boundary

The same operation also recognizes the closed `native-record-transition-v1` request branch: `protocol`, `idempotency_key`, `expected` and `transition`, without ordinary `entities` or a caller-supplied tenant/actor. OpenAPI defines the six transition shapes and the versioned expected-read groups. Structural validation preserves finite fractional registered data, requires safe integers for counts/durations, and verifies the expected schema hash's relationship to its single registry group. Parsing does not establish that any supplied readset, principal, schema, option or artifact is authentic or complete.

Native execution remains incomplete and unavailable. A structurally valid request returns HTTP503 `NATIVE_DEPENDENCY_UNAVAILABLE` with `details.dependency` and `details.repair_hint`, without native rows, notifications or ordinary-write fallback. The service must still acquire verified principal bindings, historical authority, complete scoped reads and the admitted runtime registry/reducer before implementing native effects and immutable receipt replay. Do not manufacture those prerequisites from user identity, a grant label, a hash or synthetic test fixtures.

Raw duplicate-key parsing, native signed-body admission, scoped historical read extensions, native effect/reducer/receipt writes and built-CLI native acceptance are not implemented by this validation boundary. Existing general transaction tests do not establish native readiness. Approval must only remove a hold for eligibility; a caller still needs its own fresh authenticated claim/holder readback and action take-time checks. An original receipt never grants current permission. Preserve exact body/key after uncertainty; after a conflict acquire the complete current evidence again and re-sign. Unsupported native requests must not be translated into ordinary corrections, a legacy dispatch, or a lease grant.
