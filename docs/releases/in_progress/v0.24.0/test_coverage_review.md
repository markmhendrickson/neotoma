# Test coverage review — v0.24.0

## Full suite run and environment-contamination investigation

The first `npm test` run in the release-prep worktree reported **20 failed files / 76 failed tests**. Investigation traced this to leaked operator environment variables (`NEOTOMA_DATA_DIR=/Users/markmhendrickson/data`, `NEOTOMA_BASE_URL=https://neotoma.markmhendrickson.com`, plus a real bearer token and mnemonic) inherited from the invoking shell into the worktree's `npm test` process. `vitest.global_setup.ts` only falls back to an isolated test data dir when `NEOTOMA_DATA_DIR` is unset (`process.env.NEOTOMA_DATA_DIR || vitestDir`), so with the operator's real data dir and production base URL present, tests ran against real production-adjacent state instead of an isolated fixture — explaining the `subscription_list.test.ts` cross-user isolation failures (real subscriptions already existed), `store_reference_source_parity.test.ts`'s "instance is remote" 400s (the server believed it was talking to production), and the XFF/auth-topology-parity failures (real auth topology, not the test's synthetic one). CI (`ci_test_lanes.yml`) runs `npm ci` on a fresh checkout with none of these variables set, so this contamination is specific to running locally in an environment that already has the operator's Neotoma CLI configured — not a defect in the release diff or in CI.

Re-running with those variables explicitly unset (`env -u NEOTOMA_DATA_DIR -u NEOTOMA_BASE_URL ...`) reduced the failure count to **2-3 failed tests** across two runs, all investigated individually:

1. **`tests/integration/instance_skills_initialize_effect.test.ts` > "omits the section entirely when the flag is off, leaving instructions unchanged"** — fails when a live npm-registry update-check (`getPackageUpdateNotice` in `src/server.ts`) fires during the full-suite run and prepends a "New neotoma version available (0.23.0 -> 0.23.1)" notice to the instructions string the test asserts is unchanged (the npm registry genuinely has a newer `0.23.1` published). **Confirmed pre-existing on baseline v0.23.0**: an identical clean full-suite run against the unmodified v0.23.0 tag (no `NO_UPDATE_NOTIFIER`, same machine) reproduces the exact same single failure with the exact same diff. In isolated/small runs (this file alone, or alongside its neighbor `mcp_npm_check_update.test.ts`) it passes 20/20 regardless of the update-notifier flag — the failure is a live-network race that only manifests under the full suite's timing, on both baseline and release. Not a regression.

   Correction to an earlier finding in this investigation: setting `NO_UPDATE_NOTIFIER=1` "fixes" this test but **breaks** `tests/integration/mcp_npm_check_update.test.ts` (2 tests), which explicitly exercises the update-notice mechanism and expects it non-null. `NO_UPDATE_NOTIFIER=1` is therefore not a valid workaround for full-suite runs — the two tests are in tension by design, and the correct full-suite baseline (matching CI and matching v0.23.0's own behavior) is to leave the notifier enabled and accept this one pre-existing, network-timing-dependent flake.

2. **`tests/integration/mcp_target_id_identity_conflict.test.ts` > "rejects target_id updates that would add another issue's github identity"** — intermittently failed with the store succeeding instead of throwing the expected `Identity conflict: target_id` error. Root cause traced via stack trace to a real OpenAI API call in `generateEmbedding` (`src/embeddings.ts`) failing with `429 organization_spend_limit_exceeded` — the operator's OpenAI organization has hit its configured spend limit. Verified this is unrelated to the release diff by:
   - Code inspection: the identity-conflict check (`src/services/entity_resolution.ts:914`) and the embedding call (`src/embeddings.ts`, `src/services/entity_snapshot_embedding.ts`) are both **unchanged** in this release (`git diff v0.23.0..HEAD` touches neither file). The store-warning-rule fix (`src/server.ts:6746`) only evaluates `store_warnings` rules, which the `issue` schema type used by this test does not declare — that code path is not reachable by this test at all.
   - Differential runs: baseline v0.23.0 passed 6/6 consecutive isolated runs early in the investigation window, then this same test intermittently failed on both baseline and release branch later in the window as the account's spend-limit window tightened further. The divergence tracks the account's spend-limit state at call time, not the code under test — a spend limit is a sliding/account-level condition, not a per-worktree one.
   - Conclusion: pre-existing external-dependency flakiness (live OpenAI embedding call hitting an exhausted org spend limit), not a code regression introduced by this release. No code in either of this release's two functional changes lies on this test's failure path.

Both are environment-dependent, reproducible identically on the unmodified v0.23.0 tag under the same conditions, and independent of this release's diff. Neither blocks this release.

## Code review

Both functional changes in this release were reviewed against `docs/architecture/change_guardrails_rules.md` and `docs/foundation/schema_agnostic_design_rules.md`:

- **`src/services/store_warning_rule.ts` (new) + call-site swap in `src/actions.ts` / `src/server.ts`.** Consolidates two previously-duplicated inline evaluators into one shared, heavily-tested module (702 new test lines across `tests/unit/store_warning_rule.test.ts` and `tests/integration/store_warning_condition_rule.test.ts`, the latter including a replay cassette fixture). Correctly implements "unseeded/unrecognized shape triggers a warning, not silent divergence or a throw" per `docs/foundation/schema_agnostic_design_rules.md`. Field lists are taken whole or not at all — no partial-salvage guessing. **Verdict: no blocking findings.**
- **`src/server.ts` `resolveInstructionLookupUserId()`.** Mirrors an existing, already-shipped pattern (`listTools`'s identity fallback) rather than inventing a new authentication path; a failed resolution now reports `lookup_failed: true` instead of silently returning an empty list, matching the `#2131`-era "never present a failed lookup as a confident absence" convention this codebase already established for standing rules. New/expanded test coverage in `tests/integration/instance_skills_initialize_effect.test.ts` (48 unit-suite-equivalent assertions per the module's docblock) directly exercises the recovery-path case with a session connection id present. **Verdict: no blocking findings.**
- **Documentation-only changes** (foundation/ICP consolidation, redlines.md addition, `/evaluate` locale parity): authored and merged by the operator directly (commits 690880a3e, 21cbf5013), reviewed by the pm/qa swarm panel per commit trailers, docs-only with no behavior change per the commit messages' own "Docs only. No behaviour change." statement. Out of scope for a code-level review; verified `openapi.yaml` is unchanged and no `src/` files are touched by either commit.
- **`tests/unit/mcp_instruction_token_budget.test.ts` (new, test-only commit 2851d1424).** Adds a character-budget regression ceiling for the MCP instruction payload, resolved through the same server code path that ships the payload (not the raw markdown file) so the assertion tracks what agents actually receive. Ceilings only — shrinking never fails. **Verdict: no blocking findings.**

## Verdict

**No blocking findings.** Both functional changes are narrowly scoped, matched by new regression tests that were verified to fail against the pre-fix code (per each commit's message), and reviewed against the schema-agnostic-design and change-guardrails invariants with no violations found. The two observed test failures are traced to environment contamination (fixed by isolating the shell environment) and pre-existing external-dependency flakiness (OpenAI spend limit), neither of which is on the release diff's code path.
