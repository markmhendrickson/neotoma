## Findings

1. **Alternate-path auth — production detection unification (`src/shared/environment.ts`, #2510).** Three independent, differently-precedenced production checks (`isLocalRequest` in `src/actions.ts`, the root-landing mode resolver, and webhook URL allowlisting) are collapsed into one `isProductionEnvironment()`. Precedence is fail-closed: production if `NEOTOMA_ENV` OR `NODE_ENV` says production, and an unrecognized `NEOTOMA_ENV` value (typo, unimplemented profile) is also treated as production rather than falling through silently. Covered by `tests/unit/shared_environment.test.ts` (new, 156 lines), `tests/unit/root_landing_production_env.test.ts`, `tests/unit/webhook_url_allowed.test.ts`, and `tests/unit/security_hardening.test.ts`. No residual gap identified — this closes rather than opens a widening surface (previously a locally-run production build could fail to be classified as production).
2. **Alternate-path auth — MCP development-identity scoping (`d90572508`, #2504).** The development connection identity now applies only to loopback callers with the dev setting enabled, with explicit trusted-proxy handling for same-host deployments. Narrows an existing surface; no new route added.
3. **Tenant isolation — source/file-URL reads and relationship-target ownership (`c44cee51f`, #2505).** `GET` reads on sources and file URLs are scoped to the authenticated user; `create_relationship` now requires the caller to own both endpoints, with refusals surfaced via `relationships_refused` rather than silently dropped (closing the same silent-catch class as finding 6 below). Covered by `tests/security/scoped_source_and_relationship_reads.test.ts` (38 assertions) and `tests/security/tenant_isolation_matrix.test.ts` (18 assertions, pre-existing file extended).
4. **Tenant isolation — provenance and observation reads (`4a561646c`, #2502).** `POST /get_field_provenance`, `POST /get_entity_snapshot`, and `POST /list_observations` now resolve the authenticated user and scope `entity_snapshots` / `observations` / `sources` reads to it; an out-of-scope entity id returns the same 404 as an unknown id (no existence oracle). Also fixes a latent bug where the sources read selected a non-existent `file_name` column (always returned empty) — now selects `original_filename`. Covered by `tests/security/provenance_read_scoping.test.ts` (owner reads succeed, foreign-user reads 404, both REST and MCP).
5. **AAuth / agent identity — external_actor claim downgrade (`4a561646c`, #2502).** `POST /store` no longer trusts a body-supplied `external_actor.verified_via`; it is normalized to `"claim"` unconditionally via `externalActorFromCallerInput`, and `delivery_id` is not carried over from an unverified claim. Server-verified tiers (signed GitHub webhook, AAuth token claims, grant linkage) are unchanged and do not pass through this normalizer. Covered by `tests/security/store_external_actor_claim.test.ts` and `tests/unit/external_actor_builder.test.ts`.
6. **AAuth grant admission — key binding and validation (`4cb927a81`, `0510058c5`, #2506/#2512).** A grant now admits a signed request only when its pinned key thumbprint matches the signing key; a grant with no pinned key, or one revoked/suspended, is refused on every transport with an explicit admission-reason classification. Separately, grants are validated before storage — an invalid grant now reports `grant_invalid` and is refused rather than accepted and silently unusable later. Covered by `tests/unit/aauth_admission.test.ts`, `tests/unit/aauth_grant_key_binding.test.ts`, `tests/unit/agent_grants_service.test.ts`, `tests/unit/agents_grants_import.test.ts`.
7. **Cross-tenant schema activation fallback (`a9b4f6e14`, #2356/#2365, fixed within this range).** `SchemaRegistryService.activate()` previously had a silent `candidates[0]` catch-all that could resolve to *any* row at a given `(entity_type, schema_version)` when neither the caller's user-scoped row nor the global row matched — a caller-chosen `schema_version` string on `POST /register_schema` could be crafted to collide with a foreign user's private override version, steering `activate()` onto that foreign row and deactivating it. This is a genuine pre-v0.23.1 vulnerability fixed inside this release range (not merely hardening of new code): the fallback is dropped and the call now fails closed with "Schema not found." Pinned by two new tests in `schema_scope_resolution_parity.test.ts`, verified red against the prior fallback before the fix. **This should be filed as a disclosed advisory** (see Residual risks) since it is a fixed vulnerability that existed in a previously released version (through v0.23.1), not a preventive hardening of unreleased code.
8. **Schema read/write scope-precedence unification (`a9b4f6e14`, #2356/#2365).** `listEntityTypes` previously did not select `scope` and collapsed a global/user-scoped pair with last-write-wins ordering, disagreeing with the write path's precedence (prefer user-scoped, fall back to global) in either direction depending on row arrival order. This is also a cross-user disclosure fix: the unscoped branch now filters to global rows only, closing a path where one user's private entity-type name/schema could leak to another user's `GET /schemas` / `list_entity_types` call. Covered by `tests/integration/schema_scope_resolution_parity.test.ts` and `tests/integration/schema_scope_surface_parity.test.ts` (drives all three surfaces: HTTP, MCP `list_entity_types`, MCP `describe_entity_type`, asserting they agree).
9. **Shared-graph identity confusion (`f3750a014`, #2377).** Shared-graph sign-in previously overwrote "who you are" (verified Google email) with "whose graph you operate on" (shared `user_id`), so the Inspector told a signed-in teammate they were the graph owner. Fixed by carrying both fields (`BoundIdentity`) rather than collapsing them; `GET /me` now emits `authenticated_user_id` / `shared_graph` only when they differ (unchanged response shape for the non-shared-graph majority). Data-scoping itself (`stampUserPrincipal`, `getAuthenticatedUserId`) is unchanged — still keyed on the graph user_id alone; this is an identity-display fix, not a data-isolation fix, and a regression test asserts writes under a teammate's session still land on the shared graph. Covered by `tests/integration/shared_graph_identity.test.ts` and Inspector/CLI parity tests.
10. **Relationship-type governance and cycle-check hardening (`6c29b6451`, #1972/#2357).** `register_relationship_type` is gated by a new capability, enforced in the service layer so MCP/HTTP/CLI inherit one check. The prior cycle-check in `create_relationship` was type-blind, tenant-blind (no `user_id` filter, so one tenant's edges could refuse another tenant's write), unbounded, and present on only one of four write paths; it is now opt-in per type via the registry's `acyclic` flag, scoped to type and tenant, and depth-bounded. A fail-closed fix within the same PR: an unreadable type `definition` previously parsed as `{}`, which read `acyclic` as absent and skipped the cycle-detection DFS entirely — now an unreadable definition parses as `{ acyclic: true }` (the restrictive branch), verified red/green against a malformed-row regression test. Covered by `tests/services/relationship_type_security.test.ts`, `tests/services/relationship_type_registration.test.ts`, `tests/contract/relationship_type_enum_parity.test.ts`.
11. **Proxy trust.** No new code was found reading `X-Forwarded-For`, `Forwarded`, `Host`, or `req.socket.remoteAddress` outside the canonical `forwardedForValues(req)` / `isLocalRequest(req)` helpers in `src/actions.ts`. The production-detection unification (finding 1) consolidates behavior into these same helpers rather than adding a parallel path.
12. **Local-dev widening.** `grep` for `LOCAL_DEV_USER_ID` outside `src/cli/`, `src/services/local_auth.ts`, and `tests/` turns up only comment-only references in `src/services/sandbox_mode.ts` (naming the constant in prose, no value use) and pre-existing, unchanged-in-this-range references in `src/actions.ts`. `git log v0.23.1..HEAD -- src/services/sandbox_mode.ts` is empty — that file was not touched in this release, so this is pre-existing lint noise, not a new regression. Confirmed via `npm run security:lint` (0 errors, only pre-existing warnings).
13. **Unauth public route / new Express routes.** Two new routes were added this range: `POST /register_relationship_type` and `POST /list_relationship_types` (finding 10), plus `POST /mcp` (MCP 2026-07-28 stateless transport, #2501/#2070). All three are present in `protected_routes_manifest.json` (verified via `npm run security:manifest:check` — "in sync with openapi.yaml (123 routes)"). `POST /mcp`'s stateless path resolves auth per-request via `resolveRequestConnectionId` / `resolveAuthentication` (the same logic `initialize` already used, extracted unchanged); a credential that passes the transport gate but resolves to no user now returns 401 (`MCP_AUTH_CONNECTION_INVALID` / `MCP_AUTH_UNRESOLVED`) before any method executes.
14. **MCP stateless-transport hardening follow-ups (`9b6f56e85`, #2501/#2070).** Addressed within the same PR after arch/security review: (a) process-level `SIGINT`/`SIGPIPE` listeners were registered per-constructed-instance under the stateless path (one instance per request) rather than once per process — fixed by moving registration to a single `installStdioSignalHandlers()` call on the stdio path only, with a test asserting listener count does not move across 200 constructions and 50 stateless requests; (b) connection ids were logged in full across several call sites — now logged only as a 12-hex SHA-256 fingerprint or `"absent"`, with a console/stderr spy asserting no raw id or Bearer value appears in output on either transport era.
15. **Guest-access policy widening.** No changes to `assertGuestWriteAllowed`, `routeAcceptsGuestPrincipal`, or any guest-token issuer were found in this diff.
16. **Abandoned-request abort containment (`ec7239669`, #2483/#2484) — reviewed as a hardening measure, not primarily a security fix.** Contains a crash-loop caused by an unhandled `WorkerDbAbortError`, and was itself the subject of two rounds of adversarial security re-review during development (captured in the commit history): a test-only entrypoint hook (`NEOTOMA_ACTIONS_TEST_FOLLOWUP_MODULE`) was flagged as a plausible code-injection surface (ungated `import()` of an env-supplied path at boot) and narrowed to refuse under `NODE_ENV=production` and require the path to resolve under `node_modules/` with an exact test-owned prefix; a second-round finding showed the path and the `import()` argument were checked and used inconsistently (checked as a filesystem path, loaded as a URL — percent-encoded `..` and `?`/`#` could defeat both checks), fixed by resolving via `fs.realpathSync` before checking and importing the exact checked path via `pathToFileURL(...).href`. Both fixes are regression-tested with the exact bypass strings that previously worked. This surface never shipped in a released version (introduced and hardened within the same PR before merge), so it does not warrant a standalone advisory, but is recorded here because of its severity class (code injection) had it shipped unfixed.

## Suggested negative tests

- All findings above have dedicated regression tests already merged in this range (see per-finding test file references). No additional negative test is proposed as missing.
- One gap noted for future work, not blocking this release: `tests/security/tenant_isolation_matrix.test.ts` should grow a row for the two new relationship-type routes (`register_relationship_type`, `list_relationship_types`) asserting cross-tenant registration attempts are refused, per the "New query endpoints MUST add a row" rule in `.claude/rules/change_guardrails_rules.md`. `tests/services/relationship_type_security.test.ts` covers this at the service layer but not yet via the matrix's cross-surface harness. Filed as a follow-up, non-blocking since the capability gate itself (finding 10) already enforces tenant scoping at the point of mutation.

## Residual risks

- **Finding 7 (schema activation cross-tenant fallback) is a genuine pre-v0.23.1 vulnerability, not preventive hardening.** It should be filed as a disclosed security advisory under `docs/security/advisories/` following the pattern of the existing 2026-05-21 relationship-endpoint tenant-isolation advisory, since the vulnerable code shipped in prior published versions (through v0.23.1) and the fix in this release closes it. Recommend filing before this release is announced publicly, so the advisory and the fix version are correlated. This was not done as part of this preparation pass — flagging for the release owner's decision before sign-off.
- No other residual risks identified. All other findings are either fixes for issues that never shipped (findings 14, 16) or are additive scoping/hardening with full regression coverage.
