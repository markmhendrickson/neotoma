This release tightens tenant isolation and agent identity across schema resolution, provenance reads, entity writes, AAuth grants and shared-graph sign-in, binds the server to loopback by default, adds a runtime relationship-type registry so the edge vocabulary is no longer a fixed enum, ships a new MCP 2026-07-28 stateless transport alongside the existing session-based one, scopes subscription access for entity-scoped guest tokens to the token's own grant, and records the signed-in member on writes to a shared graph.

## Highlights

- **The HTTP server binds loopback by default.** A self-hosted install listens on `127.0.0.1` unless you set `NEOTOMA_HTTP_HOST` (for example `0.0.0.0` behind Fly, Docker or a tunnel). The bundled Fly configs set it explicitly. See Breaking changes.
- **Writes land only on entities you own.** Every write entrance that can add an observation to an existing entity (entity resolution, `store`, `correct`, interpretation, import, `split_entity`, sync-conflict resolution, batch correction) now refuses an entity owned by another user with `entity_owner_conflict` instead of merging into it.
- **AAuth identity decisions key on the verified signing key.** The `operator_attested` tier and `NEOTOMA_STRICT_AAUTH_SUBS` read the identity recorded on the grant that pins the signing key (or a new `NEOTOMA_OPERATOR_ATTESTED_THUMBPRINTS` entry), and a key thumbprint can be pinned by grants under one owner only.
- **MCP OAuth local-backend codes are PKCE-bound and single-use.** `/mcp/oauth/token` now requires the `code_verifier` matching the challenge presented at authorization (codes issued through the OpenAI Custom GPT callback flow, which has no client PKCE, keep their existing server-side handling), and a code is consumed on first use.

- **Register new relationship types without a code change.** `register_relationship_type` (CLI: `neotoma relationship-types register`) and `list_relationship_types` make the edge vocabulary a runtime registry instead of a fixed enum — a consumer that needs an edge type the substrate doesn't already know no longer has to bend an existing type or simulate the edge as a field.
- **Schema reads now agree with schema writes, everywhere.** `list_entity_types`, `describe_entity_type`, and `GET /schemas` resolve the same global-vs-user-scoped schema the write path already preferred, closing both a version-disagreement bug and a cross-user schema-name disclosure.
- **A shared graph no longer tells you that you own it.** `GET /me` now reports `authenticated_user_id` (who you are) alongside `shared_graph` (whose graph you're on) instead of collapsing them, so the Inspector and CLI stop telling a signed-in teammate they are the graph's owner.
- **Relationship endpoints and provenance reads are ownership-checked.** `create_relationship` (and the relationship leg of `store`) now requires both endpoints to be entities you own; provenance and observation reads (`get_field_provenance`, `get_entity_snapshot`, `list_observations`) are scoped to the authenticated user.
- **MCP serves the 2026-07-28 stateless spec alongside existing sessions.** `POST /mcp` now dual-routes: session-less requests that declare a 2026-07-28 protocol version in `_meta` are served statelessly (per-request auth, no session state); `initialize`/`Mcp-Session-Id` clients are unaffected.
- **Subscription routes reachable by guest tokens are scoped to the token's owner.** An entity-scoped guest can create, list, inspect, cancel and stream only subscriptions wholly inside its own entity grant, and guest subscriptions use SSE delivery only.
- **Writes to a shared graph record which member made them.** Records written under a signed-in session now carry a per-instance pseudonymous member id in their provenance, so two members writing to one shared graph produce distinguishable records.

## What changed for npm package users

**CLI (`neotoma`)**

- New `neotoma relationship-types` command family: `list`, `register`, plus `--relationship-types <types>` filtering on relationship-read commands. See `docs/developer/cli_reference.md`.
- `neotoma relationships create` (and the underlying `create_relationship`/`create_relationships` calls) now require both `--source-entity-id` and `--target-entity-id` to be entities you own; an endpoint that doesn't exist and one owned by another user are refused identically, so the refusal reveals nothing about other users' data.
- `neotoma schemas update` (`update_schema_incremental`) reports `ERR_SCHEMA_SCOPE_MISMATCH` naming `guard_scope` and `found_scope` when an active schema exists in a different scope than the call checked; retry with `--user-specific` matching `found_scope` rather than running `neotoma schemas register`.
- `neotoma auth login`'s already-signed-in output now distinguishes "signed in as" (email, the verified identity) from the shared-graph id when the two differ, in both text and JSON modes.
- `neotoma request` gains `--guest-access-token <token>` (use an entity-scoped guest bearer token instead of the configured owner token; not combinable with `--skip-auth` or `--aauth`) and `--aauth` (sign the request with the configured AAuth key). `neotoma request --operation eventsStream` writes the raw SSE frames to stdout until the server closes the stream.
- `neotoma auth login` completes the OAuth exchange with a PKCE `code_verifier` and reads the connection id from the token response's new `connection_id` field.
- `neotoma mcp config` (and the install/fix offers behind it) no longer replaces an existing `neotoma` / `neotoma-dev` MCP entry that looks deliberate (a non-checkout command, `--aauth` args, AAuth env keys, or a URL-transport entry pointing at a hosted server). Replacing one requires a live interactive "yes"; `--yes` and non-TTY defaults never count, and a confirmed replacement first writes a timestamped backup of the old entry next to the config file.

**Runtime / data layer**

- One shared `isProductionEnvironment()` (`src/shared/environment.ts`) now backs the local-caller check, the root-landing page, and webhook-URL allowlisting. Production is `true` when either `NEOTOMA_ENV` or `NODE_ENV` says so, and an unrecognized `NEOTOMA_ENV` value is treated as production (with a rate-limited warning naming the value) rather than silently falling through. See `docs/operations/configuration.md` "Environments" for the operator-facing migration note — running a production-built bundle locally now counts as production even without `NEOTOMA_ENV` set, and `NEOTOMA_ENV=development` no longer overrides an ambient `NODE_ENV=production`.
- An unhandled `WorkerDbAbortError` that previously crash-looped the hosted server is now contained: a process-level listener scoped narrowly to that error type logs a structured diagnostic (stack, cause, reader-pool stats, uptime) and lets the process continue; every other unhandled rejection still exits as before.
- `relationship_snapshots.relationship_type` remains unconstrained `TEXT`; no data migration ran and the 28 built-in types validate identically after this change.
- The HTTP listener binds `127.0.0.1` by default and passes `NEOTOMA_HTTP_HOST` to the listener when set. The boot-time sandbox-mode posture and the socket that actually opens now derive from the same resolved host, and a post-bind check logs loudly if they ever disagree.
- Entity resolution and the two observation-insert paths (`createObservation`, `createCorrection`) refuse an existing entity whose owner differs from the writer (`entity_owner_conflict`). An unowned legacy row is still adopted by the first real writer, as before.
- Outbound fetches to caller-supplied URLs (subscription webhooks, entity-submission webhook mirrors, peer health checks, sync conflict resolution, outbound sync webhooks) all go through the shared host guard. Under `NEOTOMA_HOSTED_MODE` the guard refuses private, loopback and platform-internal hosts; self-hosted installs can still point webhooks and peers at loopback.
- AAuth: a key thumbprint can be pinned by `agent_grant`s under one owner only. Every entrance that sets `match_thumbprint` (grants service and routes, `store`/`correct` on REST and MCP, grants import, interpretation, restore, merge, split) refuses a thumbprint another owner already pins (`409 agent_grant_pin_conflict`), and admission refuses a key pinned under more than one owner (`grant_pin_conflict`, mapped to the deny ceiling). The identity-lookup cache is now bounded.
- MCP OAuth local backend: authorization completion mints a dedicated single-use code (new `mcp_oauth_codes` table), bound to the PKCE challenge, distinct from the connection id. Redemption requires the matching verifier and deletes the code whatever the outcome.
- `scripts/dev-proxy.js` (development only) binds loopback by default; set `PROXY_HOST=0.0.0.0` to opt in to LAN or phone testing.
- A new `member_attribution_ids` table holds a random per-instance UUID for each signed-in member, minted the first time the member's session is resolved. The request-scoped attribution context stamps it into write provenance as `authenticated_actor_id`; it is provenance only and never affects which graph is read or written.
- Subscription and event-stream routes resolve a guest token's entity grant once (`resolveGuestSubscriptionScope()` in `src/actions.ts`, with `subscriptionWithinGuestScope()` in `src/services/subscriptions/guest_scope.ts`) and apply it to subscribe, list, status, unsubscribe and `GET /events/stream`. The SSE hub revalidates the guest credential before each delivery and closes the stream after expiry, revocation or grant narrowing.

**Shipped artifacts**

- `openapi.yaml` and `dist/` reflect the new `/mcp`, `/register_relationship_type`, and `/list_relationship_types` routes plus the `update_schema_incremental` response restructuring described under Breaking changes.

## API surface & contracts

- **New operations:** `POST /mcp` (MCP 2026-07-28 stateless transport), `POST /register_relationship_type`, `POST /list_relationship_types`.
- **New response fields:** `GET /me` gains `authenticated_user_id` and `shared_graph` (emitted only when they differ from the graph-scope `user_id`, so existing consumers see an unchanged shape otherwise); `POST /agents/grants` and `PATCH /agents/grants/{id}` gain `warnings`; `POST /interpretations/create` and `POST /store` (`StoreStructuredResponse`) gain `relationships_refused`, and `StoreStructuredResponse` gains `relationships_created`.
- **`POST /update_schema_incremental` response restructured (non-breaking in practice, see Breaking changes below):** the 200 response is now a `oneOf` of the existing success shape and a new `SchemaRegistryToolErrorResponse` (`{ error: { error_code, message, hint, details } }`) carrying `ERR_SCHEMA_SCOPE_MISMATCH` / `ERR_NO_SCHEMA_FOR_ENTITY_TYPE` / `ERR_SCHEMA_MISSING_IDENTITY_CONFIG` on HTTP 200, matching the MCP tool response shape.
- **`POST /mcp/oauth/token`:** the `authorization_code` grant now requires `code_verifier`, except for codes issued through the exact OpenAI Custom GPT callback flow; the token response gains `connection_id`.
- **`AgentAttribution` gains `authenticated_actor_id`** in `openapi.yaml`: the signed-in member's write-attribution id, absent when no verified sign-in stands behind the write and withheld from responses to guest readers. It is not the same value as `GET /me`'s `authenticated_user_id`.
- **Guest subscription requests return `403 FORBIDDEN`** for a `POST /subscribe` without an `entity_ids` filter inside the token's grant, for webhook delivery or a `sync_peer_id`, and for a denied `POST /unsubscribe`; `POST /list_subscriptions` and `POST /get_subscription_status` filter to subscriptions inside the grant, and `GET /events/stream` returns `404` for a subscription outside it. Missing, invalid, expired or revoked guest credentials return `401`.
- **New error codes:** `entity_owner_conflict` (added to `StoreResolutionIssue.code` for `POST /store`'s `issues[]`; documented as a `409` on `POST /correct` and on `POST /entities/split` for `new_entity.target_entity_id`), `agent_grant_pin_conflict` (`409` on grant writes and restores), and the `grant_pin_conflict` admission reason.
- Protected-routes manifest regenerated and verified in sync with `openapi.yaml` (123 routes).

## Behavior changes

- `create_relationship`, `create_relationships`, and the relationship leg of `store`/`create_interpretation` now refuse an edge whose source or target is not owned by the caller. A refused edge is reported in the response's `relationships_refused` array (`RELATIONSHIP_ENDPOINT_NOT_FOUND` or `RELATIONSHIP_REFERENCE_UNRESOLVED`) instead of being silently dropped — previously a store carrying an unacceptable edge could return success with the edge silently absent.
- `list_entity_types`/`GET /schemas`'s unscoped read now returns only global schema rows instead of collapsing a global/user-scoped pair with last-write-wins ordering; a private, user-scoped schema override no longer leaks its name to other users via the unscoped list.
- `SchemaRegistryService.activate()` no longer falls through to an arbitrary matching row when neither the caller's user-scoped row nor the global row matches at a given `(entity_type, schema_version)`; it fails closed with "Schema not found" instead.
- The relationship cycle-check in `create_relationship` is now opt-in per type via the registry's `acyclic` flag (set on `DEPENDS_ON` and `PART_OF`), scoped to that type and tenant, and depth-bounded — previously it ran across every edge of every type with no tenant filter and no depth bound, and only on one of four write paths.
- `GET /me` reports `authenticated_user_id`/`shared_graph` only when they diverge from the graph-scope `user_id`; the Inspector sidebar and Settings page now label which id is the signed-in person and which is the shared graph, and prompt re-authentication when a pre-migration connection row has no recorded signer identity.
- The sources read behind `get_field_provenance` previously selected a non-existent `file_name` column and always returned an empty list; it now selects `original_filename` and returns real results, scoped to the authenticated user.
- Subscription routes called with an entity-scoped guest token now act only on subscriptions whose watched entities are all inside the token's grant; owner and local-development callers are unchanged.
- Writes made under a signed-in session (`store`, `correct`, relationship observations, timeline events, sources and interpretation runs, over REST and both MCP transports) record `provenance.authenticated_actor_id`. Static bearer tokens, key-derived MCP tokens, local no-auth, AAuth grants, sandbox sessions and local CLI dispatch write none, and earlier records are not rewritten. Deletes, restores, merges and splits are not yet covered.

## Agent-facing instruction changes (by channel)

`docs/developer/mcp/instructions.md` and `docs/developer/cli_agent_instructions.md` gained the following. The first item ships through CLI-installed agent rule files only: it sits outside the MCP instruction block, so MCP clients and `neotoma instructions print` do not receive it. The remaining items are in the MCP instruction block and reach every client.

- **Relationship type discovery and registration** (CLI-installed rule files only) — a new section instructing agents to call `list_relationship_types` before using an unfamiliar edge type, and `register_relationship_type` (default user scope; global scope requires an explicit grant) when the meaning is absent. Explains the `empty_reason` field (`registry_unseeded` vs `filtered_to_empty`) so an empty result is never mistaken for "no vocabulary exists," and gives a migration recipe for re-typing historical `related_to` + `metadata.relation` edges into a newly registered type.
- **Relationship endpoints must be owned entities** — agents must check `relationships_refused` after any `store`/`create_interpretation` call that named relationships, and resolve `RELATIONSHIP_ENDPOINT_NOT_FOUND` by storing the missing entity first rather than assuming the edge was created.
- **Schema scope mismatch** — agents hitting `ERR_SCHEMA_SCOPE_MISMATCH` on `update_schema_incremental` must retry with `user_specific` matching `details.found_scope`, and must not call `register_schema` for that error code (doing so risks creating a second dual-active schema row).
- **MCP 2026-07-28 clients** — a transport-layer pointer describing the stateless request shape (`params._meta` protocol version, no `initialize`/session), `server/discover` for instructions/capabilities, and the `Mcp-Method`/`Mcp-Name` header contract.
- **Guest subscription rules** (MCP instruction block, `[SUBSTRATE SUBSCRIPTIONS]`) — an entity-scoped guest must supply its guest bearer token and a non-empty `entity_ids` filter wholly inside its grant, may only use `delivery_method: sse`, and gets `403 FORBIDDEN` (creating nothing) otherwise; the section also documents the guest read, status, unsubscribe and stream behavior and the `neotoma request --operation eventsStream --guest-access-token` form. Agents neither set nor read `authenticated_actor_id`, so no agent instruction changed for it.

## Internal changes

- `src/shared/environment.ts` extracted as the single production-detection module, replacing three independently-maintained copies.
- `services/relationship_types/` added as a sibling registry to `schema_registry`, deliberately not sharing its table or inheriting four of its known defects (no unique constraint, no index, non-transactional register, unscoped `activate()` update).
- `peekCachedDb()` added to `repositories/db/connection.ts`: a synchronous, non-opening accessor so the new abort-containment handler can read reader-pool diagnostics without itself awaiting a DB open.
- `Error.stackTraceLimit` raised to 100 at startup so future unhandled-rejection diagnostics carry async stack frames.
- Test catalog regenerated multiple times across this range to stay current with new integration/unit suites (`npm run generate:test-catalog`).

## Fixes

- `list_relationship_types` explains an empty result (`registry_unseeded` / `filtered_to_empty`) instead of returning a bare empty list when the built-in relationship types are missing for the serving process; they are reseeded once on first read or write.
- A millisecond-racing duplicate relationship-type registration previously surfaced as a raw 500 (`relationship_type_registration_failed`); it is now absorbed as "already registered."
- An unreadable relationship-type `definition` row previously parsed as `{}`, which read the `acyclic` flag as absent and skipped cycle-detection entirely; it now parses as `{ acyclic: true }` (the restrictive branch), so a corrupt row can never escape the cycle check.
- `describe_entity_type` and `update_schema_incremental`'s existence guard previously disagreed on which scope to check, so a type with an active user-scoped schema could report `ERR_NO_SCHEMA_FOR_ENTITY_TYPE` moments after `describe_entity_type` returned its schema. The guard now distinguishes "no schema in any scope" from "schema exists in a different scope" (`ERR_SCHEMA_SCOPE_MISMATCH`), and the old hint (which recommended `register_schema` — the exact action that produces a dual-active-row condition) is corrected for the scope-mismatch case.
- The MCP development-connection identity now applies only to loopback callers with the development setting enabled, with explicit trusted-proxy handling for same-host deployments.

## Breaking changes

- **`POST /update_schema_incremental [200]` response schema restructured — non-breaking in practice, but flagged by the automated diff tool.** The OpenAPI breaking-change diff (`npm run openapi:bc-diff`) reports 9 "removed-response-field" entries (`success`, `entity_type`, `schema_version`, `fields_added`, `fields_removed`, `canonical_name_fields`, `activated`, `migrated_existing`, `scope`) for this operation. These fields were NOT removed: the response schema changed from a flat `type: object` to `oneOf: [<unchanged success shape>, SchemaRegistryToolErrorResponse]`, and the diff tool does not traverse into `oneOf` branches, so it reports the flat top-level properties as gone when they are simply nested one level deeper inside the first `oneOf` arm. Every field a client previously read from a successful response is present at the same path when the response is successful. **Migration:** none required for existing success-path consumers. A client that wants to distinguish the new structured-error shape on HTTP 200 (as opposed to a thrown exception) should check for the presence of `error.error_code` in the response body, matching the MCP tool response shape used by `ERR_SCHEMA_SCOPE_MISMATCH` / `ERR_NO_SCHEMA_FOR_ENTITY_TYPE` / `ERR_SCHEMA_MISSING_IDENTITY_CONFIG`.
- **The HTTP server binds `127.0.0.1` by default.** Previously the listener bound all interfaces and `NEOTOMA_HTTP_HOST` was read only for a boot-time check. **Migration:** any deployment reached over a network interface (Docker, a VM, a LAN host, or a custom Fly config that does not inherit the bundled `fly*.toml`) must set `NEOTOMA_HTTP_HOST=0.0.0.0` or the specific interface address. The bundled Fly configs already set it.
- **`POST /mcp/oauth/token` requires `code_verifier` for the `authorization_code` grant (outside the OpenAI Custom GPT callback flow), and the code is no longer the connection id.** **Migration:** OAuth clients must send the PKCE verifier matching the challenge they sent to `/mcp/oauth/authorize` (standard MCP OAuth clients already do). A client that redeemed the connection id as the code, or read the connection id from the code, must read `connection_id` from the token response instead. Upgrade the `neotoma` CLI and the server together: a v0.24.0 CLI's `auth login` fails with "Token response did not include connection_id" against a server older than v0.24.0, and an older CLI cannot complete login against a v0.24.0 server because it sends no verifier.
- **Writes that resolve to another user's entity are refused with `entity_owner_conflict`.** `POST /store` reports it in `ERR_STORE_RESOLUTION_FAILED` `issues[]`; `POST /correct`, `POST /entities/split` (`new_entity.target_entity_id`) and the MCP equivalents return `409` / `InvalidRequest`. **Migration:** none for single-user or tenant-scoped installs. A caller relying on a fixed entity id shared across users must store its own entity instead.
- **`operator_attested` is no longer derived from the agent token's own `iss`/`sub`.** It is granted only to a signing key listed in `NEOTOMA_OPERATOR_ATTESTED_THUMBPRINTS`, or pinned by an active `agent_grant` whose recorded `match_iss` / `match_iss:match_sub` is in `NEOTOMA_OPERATOR_ATTESTED_ISSUERS` / `NEOTOMA_OPERATOR_ATTESTED_SUBS`. `NEOTOMA_STRICT_AAUTH_SUBS` compares `X-Agent-Label` with the pinning grant's `match_sub`. **Migration:** operators using the issuer/sub allowlists must make sure each attested agent's key is pinned by an active grant with those `match_iss`/`match_sub` values, or add its thumbprint to `NEOTOMA_OPERATOR_ATTESTED_THUMBPRINTS`.
- **A key thumbprint can be pinned by grants under one owner only** (`409 agent_grant_pin_conflict` on write or restore; `grant_pin_conflict` at admission). **Migration:** if two owners pinned the same key, keep the grant under the owner that should hold it and revoke or re-key the other.
- **Hosted mode refuses outbound fetches to private, loopback and platform-internal hosts** for webhooks, webhook mirrors, peer health checks and sync. **Migration:** none for self-hosted installs (`NEOTOMA_HOSTED_MODE` unset). Hosted operators must point webhooks and peers at publicly routable hosts.
- **`neotoma mcp config --yes` no longer replaces a deliberate MCP entry.** **Migration:** run it interactively and answer the dedicated prompt, or edit the harness config by hand.
- **Entity-scoped guest tokens can only create SSE subscriptions on their own entities.** A guest `subscribe` without an in-grant `entity_ids` filter, with `delivery_method: webhook`, or with `sync_peer_id` now returns `403 FORBIDDEN` and creates nothing; guest `list_subscriptions` omits subscriptions outside the grant. **Migration:** none for owner tokens. A guest integration that created webhook or type-/event-only subscriptions must move to SSE subscriptions on the entities its token grants, or use an owner token.
- **Relationship edges require both endpoints to be entities the caller owns.** On v0.23.x, `POST /create_relationship`, MCP `create_relationship` / `create_relationships`, and the relationship leg of `store` / `create_interpretation` accepted an edge whose source or target did not exist or belonged to another user, and wrote it. A direct `create_relationship` call is now refused (REST `404 RESOURCE_NOT_FOUND` with a structured `details.hint`; MCP `InvalidParams` error whose data carries the same `hint`); the MCP `create_relationships` batch leaves that edge out and lists it in `errors[]` with `success: false`; `store` and `create_interpretation` succeed but report the edge in `relationships_refused` (`RELATIONSHIP_ENDPOINT_NOT_FOUND` / `RELATIONSHIP_REFERENCE_UNRESOLVED`) without writing it. **Migration:** store the endpoint entity first, or reference it by index in the same `store` call, then check `relationships_refused` after every `store` / `create_interpretation` that names relationships, and `errors[]` after every `create_relationships` batch. Pinned by the legacy-payload fixture `v0.23.x/create_relationship_unowned_target` (flipped to `rejected`); see `tests/contract/legacy_payloads/CHANGES.md` § v0.24.0.
- Apart from the relationship-endpoint ownership refusal above, these rejections are not yet represented in the legacy-payload corpus (`tests/contract/legacy_payloads/`); coverage lives in the suites named under Security hardening. See `test_coverage_review.md`.
- No other breaking changes. The 13 OpenAPI enum blocks, Zod enum, tool-schema enums, inspector constant, and CLI casts that previously hardcoded the relationship-type vocabulary are removed in favor of `list_relationship_types`, but `relationship_snapshots.relationship_type` remains unconstrained `TEXT` and all 28 built-in types continue to validate identically — no caller-visible enum was narrowed, and no existing edge type stops working.
