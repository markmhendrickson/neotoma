This release absorbs the previously-abandoned v0.21.1 candidate (schema-registry metadata preservation, atomic backup snapshots, MCP shim port self-healing) and adds four more fixes: two hosted-server outage mitigations for a recurring clean-exit bug (#2094), and a Codex/session-portability transcript-ingest fix that also closes a total-failure bug in `--import-transcripts --apply`.

## Highlights

- **Hosted server restarts on a clean exit, not just a crash.** Production exits with code 0 roughly every 12 minutes with no error (#2094; root cause still unknown). Fly's default `on-failure` restart policy — like `min_machines_running` alone — ignores exit code 0 by definition, so the machine stayed down until an inbound request happened to wake it (measured cold start: 33-45s with intermittent 503s, against a normal 0.2s). An earlier fix in this range added an HTTP health check under `[[http_service.checks]]`, but that is a *service* check that only governs load-balancer routing — it does not restart a machine, and the comment claiming otherwise was corrected. The fix that actually closes the gap sets `[[restart]] policy = 'always'`, the only Fly restart policy that covers a code-0 exit. Verified on a hosted instance: no exits in ~40 minutes where they had been occurring every ~16, and worst-case latency dropped from 45s to ~2.3s. Both changes are safety nets, not a fix for #2094 itself — the process should not be exiting at all, and the `beforeExit` diagnostics landed in this range never fired during the clean-exit event, which argues against "event loop drains" as the root cause.
- **`update_schema_incremental` no longer drops row-level `metadata`.** The incremental-update path registered a new schema version and activated it, but never carried the current active row's `metadata` (`guest_access_policy`, `icon`, etc.) into the new version, so the new active row was written with `metadata: {}`. Since `guest_access_policy` resolves from `SchemaMetadata` on the active row, every incremental field-add or field-removal silently reverted the entity type to the `closed` guest-access default, breaking all token-gated guest reads of that type (the #1977 symptom fixed here). The fix merges the current active row's metadata into the newly registered version, with an optional `metadata` option layered on top so a caller can still override individual keys. Remaining #1977 scope (`register_schema` parity, response-visible `access_policy`/`warnings[]`, effect/cross-surface tests, docs) is tracked in #2069 — not claimed closed by this release.
- **`backup create` snapshots the database atomically instead of copying it live.** The command copied the SQLite database and its `-wal` file as two independent `fs.copyFile` calls, with no checkpoint and no read lock. Any write committing between the two copies left the WAL's frame checksums invalid against the main file's header — restoring the pair failed with `SQLITE_CORRUPT`, while the command still reported `"verified": true` (verification only checked file size > 1KB). The fix uses `VACUUM INTO` for a single atomic, transaction-consistent snapshot, then runs `PRAGMA integrity_check` and fails the command unless it returns `ok`. Closes #2075.
- **The MCP shim discovers the live port instead of dying on a stale port file.** When every candidate port file failed its TCP probe, the resolver fell back to a hardcoded port for the profile; if the server was actually bound elsewhere, that fallback was dead too and the shim exited immediately with only "Could not attach to MCP server." The resolver now probes the canonical ports for the profile before falling back, uses the first reachable one, and self-heals the port file so the next start resolves on the fast path. Closes #2087.
- **`--import-transcripts` now sees live Codex sessions, and `--apply` no longer fails every import.** Codex writes live sessions to a date-partitioned `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` tree; discovery only globbed the legacy `~/.codex/archived_sessions/` path, so active sessions were silently skipped (closes #2072). The parser also only accepted `text`/`output_text` content blocks, while live rollouts encode user turns as `input_text` — every user message was dropped even once the file was found. Against a 57-rollout local corpus, parsing went from 0 messages to 725 across 57/57 rollouts. Separately, the import path now attaches `agent_session` and `session_transcript` entities (closes #2073) so a transferred transcript can be re-located and resumed — `cwd` is load-bearing here: Cursor keys its on-disk chat directory by `md5(cwd)`, so without it a transferred chat resumes into an empty thread instead of erroring. While wiring that in, a **pre-existing total failure** was found and fixed: attaching entities upgrades the request to the structured `POST /store` path, which requires `idempotency_key`; the CLI sent none, so every real `--import-transcripts --apply` was rejected with a 400 `VALIDATION_ERROR` — no transcript, raw or otherwise, was ever stored via this flag. Fixed by keying on `transcript-import-<content_hash>`, which also makes re-imports of identical bytes idempotent by construction.

## Security hardening

Fixes the `updateSchemaIncremental` metadata-drop symptom reported in #1977 (unrelated field-add/remove no longer silently resets `guest_access_policy`/`metadata` to `{}`). The failure was invisible at write time; the only symptom was a 403 or empty result on a later guest read. The fix is additive/preserve-only. #1977's remaining acceptance criteria (`register_schema` version-activation parity, response-visible `access_policy`/`warnings[]` contract, effect-verified guest/token read test, cross-surface parity tests, docs) are not shipped in this train; tracked in #2069 — do not treat #1977 as fully closed until #2069 lands.

`agent_session` and `session_transcript` are now seeded schema types with `canonical_name_fields` keyed on `(harness, native_session_id)` and `content_hash` respectively, so re-import dedupes by construction rather than by convention.

The restart-policy and health-check changes are Fly deployment configuration only, with no auth, access-control, or network-exposed application surface. The backup and MCP-port fixes are CLI-local reliability fixes with the same profile. `security:classify-diff` scoped the release `sensitive=true` (`src/actions.ts` is in the `auth-middleware` file allowlist, which flags on file identity rather than diff content); the only change to that file in this range is boot-time schema seeding and process-exit diagnostics, neither of which touches `isLocalRequest`, auth resolution, or route registration. `security:lint` (0 errors), `security:manifest:check` (116 routes, in sync), and `test:security:auth-matrix` (18/18, 1 skipped, unchanged from baseline) all pass clean. See `docs/releases/in_progress/v0.21.2/security_review.md` for the full adversarial pass (sign-off: `yes`).

## What changed for npm package users

- **`neotoma backup create`** now snapshots the SQLite database with `VACUUM INTO` instead of a raw file copy, and fails the command (non-zero exit, error naming the on-disk path) if `PRAGMA integrity_check` does not return `ok`. The backup manifest gains a `db_snapshot_method: "vacuum_into"` field. `backup restore` behavior is unchanged and still supports older file-copy backups that include a `-wal`.
- **`neotoma --import-transcripts`** now discovers live Codex sessions under `~/.codex/sessions/YYYY/MM/DD/` in addition to archived ones, reports a per-harness scan summary (Codex splits live vs. archived counts), and names every scanned location on a zero-match result. `--apply` no longer fails outright — the missing `idempotency_key` that rejected every real import with a 400 is fixed. Imports from harness sources (Claude Code, Codex, Cursor) now also store `agent_session` + `session_transcript` entities alongside the raw transcript, enabling session resume; non-harness sources (ChatGPT/Slack exports) are unaffected since they have no resumable session by design. New doc: `docs/developer/cli/transcript_ingestion.md`.
- **The MCP shim (`scripts/lib/neotoma_mcp_resolve_downstream_url.sh`)** self-heals a stale or unreachable port file by probing the canonical dev/prod ports and rewriting the port file on success, instead of falling straight to a hardcoded fallback that may also be wrong.
- No other CLI, MCP tool, or API request/response shape changes. The schema-registry fix is internal; callers of `update_schema_incremental` see no contract change.

## API surface & contracts

- No new MCP tools, no new Express routes.
- Two new registered entity types boot-seeded (not exposed as new API surface): `agent_session`, `session_transcript`.

## Behavior changes

- **Operator-visible (hosted deployment):** the production Fly machine now restarts automatically on any process exit, including the recurring clean exit under investigation in #2094, instead of remaining down until an inbound request wakes it. Expect materially lower tail latency and fewer intermittent 503s on the hosted instance; no client-visible contract change.
- **Operator-visible (hosted deployment, no graceful drain on SIGTERM):** the new exit-diagnostics change also adds `SIGTERM`/`SIGINT`/`SIGHUP` handlers that call `process.exit(0)` immediately, with no `server.close()` or in-flight-request drain. Combined with `[[restart]] policy = 'always'`, every routine Fly deploy or platform-initiated restart now sends `SIGTERM` into this immediate-exit path, so a request in flight at that moment can be dropped rather than completed. This is new behavior versus v0.21.0 (no signal handler previously existed). Flagged in review as a follow-up: either add a bounded drain window before exit, or confirm Fly's proxy layer already drains connections before delivering `SIGTERM` and this is a non-issue in practice. Not blocking for this release — the net effect of this range is still strictly fewer outages (see above) — but operators should be aware a deploy can drop an in-flight request until this is resolved.
- **Operator-visible (schema registry):** entity types with row-level metadata (`guest_access_policy`, `icon`, bundle info) that go through an incremental schema update now keep that metadata by default instead of it being silently reset to `{}`.
- **Operator-visible (backup):** `neotoma backup create` on a live, actively-written database now always produces a restorable backup; previously it could silently produce one that fails to restore. Backup creation may take marginally longer since `VACUUM INTO` rewrites the database rather than copying bytes directly, but the result is guaranteed consistent.
- **Operator-visible (MCP shim):** a stale port file no longer causes an unrecoverable "Could not attach to MCP server" failure when the actual server is reachable on one of the profile's canonical ports.
- **Operator-visible (transcript import):** `--import-transcripts --apply` now succeeds where it previously failed on every invocation; Codex users on current CLI versions now have their live sessions discovered and imported for the first time.

## Internal changes

- `fly.toml`: adds `[[http_service.checks]]` (routing-only health check) and `[[restart]] policy = 'always'`; corrects an inaccurate comment that attributed restart behavior to the service check.
- `src/actions.ts`: adds `beforeExit`/`exit`/signal diagnostics at the HTTP server entrypoint, logging `process.getActiveResourcesInfo()` so a future clean-exit event names what held the event loop open.
- `src/services/schema_registry.ts`: `updateSchemaIncremental` now merges `currentSchema.metadata` with an optional `options.metadata` override before calling `register()`.
- `src/cli/index.ts`: `backup create` replaces the two-file `fs.copyFile` DB snapshot with a `VACUUM INTO`-based atomic snapshot plus `PRAGMA integrity_check` verification.
- `src/cli/discovery.ts`, `src/cli/transcript_parser.ts`, `src/cli/onboarding_transcript_import.ts`: live Codex rollout discovery (`findCodexSessionRollouts`), `input_text` content-block parsing, per-harness `ParsedSessionContext` (cwd/gitBranch/version), `agent_session`/`session_transcript` derivation and attachment, `idempotency_key` on transcript-entity stores, and degraded-import classification (`kind: "expected" | "unexpected"`).
- `src/services/sessions/seed_schema.ts`: new boot-time seeder for `agent_session` and `session_transcript`, following the existing issue/plan/skill seeder pattern; idempotent, additive-only, fail-soft.
- `scripts/lib/neotoma_mcp_resolve_downstream_url.sh`: adds a port-discovery probe step before the hardcoded fallback, with self-healing rewrite of the resolved port file.

## Fixes

- **Hosted server stayed down after its recurring clean exit** (#2094 mitigation). Root cause of the exit itself remains unknown; `[[restart]] policy = 'always'` covers the code-0 case that the default `on-failure` policy and the HTTP service check both miss.
- **Incremental schema updates silently reset `guest_access_policy` and other row-level metadata to `{}`** (partial fix for #1977 — remaining scope in #2069).
- **`backup create` produced unrestorable backups under concurrent writes, while reporting success** (closes #2075).
- **MCP shim died with an unhelpful error when its port file was stale** (closes #2087).
- **`--import-transcripts` never discovered live Codex sessions and dropped every user message from rollouts it did find** (closes #2072).
- **Transcript imports carried no session identity, so a transferred transcript could not be located or resumed** (closes #2073).
- **Every real `--import-transcripts --apply` invocation failed with a 400 `VALIDATION_ERROR`** — a regression introduced while implementing the #2073 fix in this same range, caught and fixed before release by attaching a content-hash-derived `idempotency_key`.

## Breaking changes

None. All seven commits in this range are fixes, internal reliability work, or deployment configuration. The schema-registry fix is additive/preserve-only; the backup fix changes only the on-disk snapshot mechanism (`backup restore` behavior unchanged); the MCP shim fix adds a discovery step before an existing fallback; the transcript-ingest fixes make a previously-broken flag work and add optional session-identity entities without changing the flag's existing contract; the Fly config changes affect only hosted-deployment restart/health behavior, not any client-facing API.
