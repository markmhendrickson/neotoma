## Findings

Range `v0.25.0..HEAD` is 19 commits and 259 files. The classifier flags five concerns. Most of the volume is store, correction and lifecycle work. The security-relevant changes are: relationship grant scoping (#2525), the WebSocket bridge bind (#2577), Docker context exclusion (#2609), three newly declared write routes (#2397, #2528), conditional and keyed-resume store (#2614, #2651), `data_origin` (#2636), lifecycle cutover (#2618) and the executed retrieval contract (#2612).

- **openapi-security / protected-routes-manifest / security-gates (`openapi.yaml`, `scripts/security/protected_routes_manifest.json`).** Three operations are added. All three are `requires_auth: true` and `sandbox_allowed: none`, with 401 expected without auth: `POST /corrections/transaction` (`correctTransaction`), `POST /entities/{id}/batch_correct` (`batchCorrectEntity`) and `POST /patch_array_item` (`patchArrayItem`). No `security:` block was removed, and no route moved to the unauth allow-list. `security:manifest:check` is in sync at 126 routes (110 protected, 9 runtime-only unauth). `batch_correct` is not a new handler. It existed at v0.25.0 (`src/actions.ts` around line 5518 at the tag) and is only newly declared in the spec and manifest. No finding.
- **auth-middleware (`src/actions.ts`).** The diff does not touch `isLocalRequest`, `forwardedForValues`, `isProductionEnvironment` or the auth middleware order. It adds no `Host` or `X-Forwarded-For` read. A grep over all added lines under `src/` finds no new reference to `LOCAL_DEV_USER_ID`, `assertExplicitlyTrusted`, `NEOTOMA_TRUST_PROD_LOOPBACK`, `remoteAddress`, forwarded headers or `routeAcceptsGuestPrincipal`. `resolveHttpBindHost` (`src/actions.ts:13736`) now delegates to `src/shared/bind_host.ts` with the same loopback default, and `isLoopbackHost` is a re-export. Removing the `assertGuestWriteAllowed` import is part of a move, covered below. No finding.
- **Store admission refactor (`src/services/store_admission.ts:46-220`).** Seven checks moved out of `storeStructuredForApi` into `preflightStructuredStoreAdmission`: the guest access-policy check, usage_digest redaction, the entity capability check, the relationship-type registration check, the protected-type guard, grant pin uniqueness and flat-packed rejection. The code moved intact. `storeStructuredForApiUnguarded` calls the preflight before the new conditional branch (`expected_entity_absent`) and before plan mode, so neither new path skips admission. The keyed-write wrapper (`runKeyedStoreWrite`) keys its in-flight map on `[userId, idempotencyKey]` (`src/services/store_write_state.ts:273`), and every `sources` read and update there filters `.eq("user_id", userId)`. No finding.
- **New write routes: user scoping and capability parity with `/correct`.**
  - `POST /corrections/transaction` (`src/actions.ts:12369`) resolves the user through `getAuthenticatedUserId` and overwrites the body `user_id` with it. `applyCorrectionTransaction` (`src/services/correction_transaction.ts:128-140`) rejects unknown top-level keys and enforces `correct` on every supplied `entity_type`. It then requires the stored type to equal the supplied type (`:197-201`), so the capability decision is in effect made on the stored type. Every entity loads through `getEntityWithProvenance(id, false, user_id)`, which applies `.eq("user_id", userId)` (`src/services/entity_queries.ts:999-1000`), so a foreign id returns `RESOURCE_NOT_FOUND`. Each field write goes through `createCorrection`. That still runs attribution policy, `assertCanWriteProtected`, override policy, the fail-closed ownership guard and instance store policy (`src/services/correction.ts:261-365`). The MCP twin (`src/server.ts:8261`) uses the same service. The test "rejects an entity outside the requesting graph before writes" in `src/services/correction_transaction.test.ts` passes. Parity with `/correct` holds.
  - `POST /patch_array_item` (`src/actions.ts:12567`) resolves the stored entity type under the authenticated user before authorization (`loadArrayItemPatchTarget`, `src/services/array_item_patch.ts:257-270`). It then enforces `correct` on the stored type (`:12599`) and runs `assertCanWriteProtectedBatch`. The MCP twin (`src/server.ts:8465-8494`) is identical. It is the only one of the three routes behind `writeRateLimit`. Parity with `/correct` holds.
  - **`POST /entities/{id}/batch_correct` (`src/actions.ts:5539-5591`): capability bypass (Medium, pre-existing, now declared).** The handler is owner-scoped: the entity lookup filters `.eq("user_id", userId)`, and `applyBatchCorrection` runs a `getEntityWithProvenance` precheck, covered by `tests/services/by_id_write_ownership_conflict.test.ts`. But the route never calls `enforceAgentCapability("correct", ...)`, and neither does `src/services/batch_correction.ts` or `createCorrection`. Take an AAuth-admitted agent whose grant lacks `correct` for type X, for example a grant with only `store` on `task`. Through this route it can correct any of its owner's non-protected X entities. `/correct`, `/patch_array_item` and `/corrections/transaction` refuse the same request with 403 `capability_denied`. This is not a tenant-isolation hole. The write stays in the caller's own graph, and `assertCanWriteProtected` inside `createCorrection` still gates protected types such as `agent_grant`. The handler is unchanged from v0.25.0, so this release does not introduce the gap, but it does newly document the route as part of the contract. Follow-up: after the owner lookup, add the same block the sibling routes use (`contextFromAgentIdentity`, `enforceAgentCapability("correct", [entity.entity_type])`, `assertCanWriteProtectedBatch`), plus a negative test.
- **Conditional store (`expected_entity_absent`, #2614).** Every observation, source, entity and snapshot read in `src/services/store_conditional.ts` filters `.eq("user_id", options.userId)`. `store_condition_keys` rows are keyed by `(user_id, key_hash)`. `assertConditionalEntityAbsent` (`src/services/store_condition_keys.ts:363-389`) reads `entities` by id without a user filter. That is deliberate: a row owned by another principal raises the existing owner-conflict error, so the write cannot adopt it. See the residual risk on existence disclosure.
- **`data_origin` (#2636) and `include_cleared_fields`.** `collectSnapshotDataOrigins` reads the cited observations with `.in("id", ...).eq("user_id", userId)` (`src/services/provenance_data_origin.ts:165-168`), so a snapshot cannot surface another tenant's origin claim. `include_cleared_fields` on `/get_entity_snapshot` requires a `userId`, because `getEntityWithProvenance` refuses the projection without one. It returns 404 for a deleted entity. No finding.
- **Executed retrieval contract (#2612).** `listActiveSchemas` now uses `scope.eq.global,user_id.eq.<userId>` plus a post-filter (`src/services/schema_registry.ts:1360`). `userId` comes from the authenticated principal, never the request, so the filter string cannot be injected. The new `read_contract` envelope discloses only entity types in the caller's own or global catalog. When a legacy search type hint resolves to a foreign private schema, the envelope reports `applied_type_scope_redacted` with a digest and never shows the name (`src/shared/action_handlers/entity_handlers.ts:1381-1397`). The entities themselves stay user-scoped. The test "bounded domain diagnostics use own/global catalog fields and never foreign private fields" in `tests/integration/entity_read_contract.test.ts` pins the non-disclosure. No finding.
- **sync (`src/services/sync/peer_sync_batch.ts:93`).** The only change wraps the outbound snapshot loop in `filterCurrentLifecycleRecords(snaps, params.userId)`. Once a lifecycle cutover is recorded, this keeps entities the owner has deleted out of what is sent to a peer. It only removes rows. It does not change peer authentication, webhook signing or which user's rows are selected, so trust is narrowed, not widened. No finding.
- **Lifecycle cutover (#2618).** The cutover, migration and manifest code under `src/maintenance/` and `src/services/entity_lifecycle_*` runs instance-wide by design, but no HTTP route or MCP tool invokes it. Only the CLI and offline maintenance path reach it. The read-side authority checks it adds (`/get_entity_snapshot`, peer sync) are user-scoped and fail closed with 500 when authority cannot be acquired. No finding.
- **MCP WebSocket bridge bind (#2577, `src/mcp_ws_bridge.ts:15,30-42`).** The bridge spawns an MCP child process per connection with no authentication before the spawn, and before this change it listened on all interfaces. It now binds `127.0.0.1` unless `NEOTOMA_WS_HOST` is set. On a listen error it exits instead of falling back to a wider bind, and it logs the address it actually bound. This narrows exposure. `tests/security/ws_bridge_bind_host.test.ts` passes (8 tests). Operators who need remote access must now opt in explicitly.
- **Docker contexts (#2609, `.dockerignore:28`).** The pattern widened from `**/.env` to `**/.env*`, so environment-file variants (development, production, backups) no longer enter build contexts or image layers. This narrows exposure.
- **Agent-initiated file-read provenance (#1934, caa0abc46).** This change is instructions only (`docs/developer/mcp/instructions.md`, `docs/developer/cli_agent_instructions.md` and eval fixtures). It tells agents to persist the bytes of files they read themselves. Secret-bearing files are exempt: for keys, env-style config and token files, agents store only a redacted derived record. Nothing on the server enforces the exemption. See residual risks.
- **1. Alternate-path auth.** No new channel reaches a privileged path without authentication. The three newly declared routes require auth and resolve the user through `getAuthenticatedUserId`. The MCP twins of `correct_transaction` and `patch_array_item` resolve the user through the server's `getAuthenticatedUserId`. The WebSocket bridge, the one transport that is unauthenticated by design, is now loopback by default. The one parity gap is the capability check on `batch_correct` (above). That gap limits what an already authenticated caller may do; it is not an auth bypass.
- **2. Proxy trust.** No new reads of `X-Forwarded-For`, `Forwarded`, `Host` or `req.socket.remoteAddress`. Diff-scoped `security:lint --base v0.25.0` reports 0 warnings.
- **3. Local-dev widening.** No new reference to `LOCAL_DEV_USER_ID`, `assertExplicitlyTrusted`, `NEOTOMA_TRUST_PROD_LOOPBACK` or a sandbox shortcut. The new env var `NEOTOMA_WS_HOST` widens only the bridge bind, and only when an operator sets it. The repo-wide `local-dev-user-widening` warnings in `sandbox_mode.ts` and `harness_force_mode.ts` are pre-existing and unchanged.
- **4. Unauth public route.** No new unauthenticated route. The three manifest additions require auth (see the first bullet).
- **5. Guest-access policy widening.** `assertGuestWriteAllowed` moved unchanged from `src/actions.ts` to `src/services/store_admission.ts:80-90`, with the same `isGuest && !bypassGuestStoreAccessPolicy` condition. `routeAcceptsGuestPrincipal` and the guest-token issuers are untouched. No entity type became newly reachable by guests.
- **6. AAuth / agent identity downgrade.** #2525 tightens AAuth rather than loosening it:
  - A `create_relationship` grant entry must now carry `relationship_types`. Absent or empty `relationship_types` denies.
  - A single entry must cover the relationship type and both endpoint entity types (`enforceAgentRelationshipCapability`, `src/services/agent_capabilities.ts:575-640`).
  - An endpoint that does not resolve owner-scoped fails closed (`src/services/relationship_write_capability.ts:155-167`).
  - `validateCapabilities` rejects a malformed `relationship_types` value instead of reading it permissively (`src/services/agent_grants.ts:366-390`).
  - The gate runs on REST and MCP store, `create_relationship(s)`, `restore_relationship`, `delete_relationship` (`src/actions.ts:11633`) and schema reference linking, and per edge inside `relationshipsService.createRelationship`.
  - The default registry drops the forwarder's `create_relationship` entry.
  
  Grants written before #2525 lose the ability to write edges; this is the documented breaking change. `tests/contract/relationship_write_grant_contract.test.ts` passes (4 tests). No path makes auth easier to satisfy without a verified `aa-agent+jwt`.
- **Minor: REST and MCP store treat deny-ceiling signers differently (Low).** REST store skips the up-front relationship check for any unadmitted AAuth signer (`if (capabilityCtx && !isGuest)`, `src/services/store_admission.ts:129`). The shared helper that MCP store uses does enforce signers whose grant is revoked, suspended or pin-conflicting, which is the `deny` ceiling (`src/services/relationship_write_capability.ts:80`). On both paths `createRelationship` still refuses the edge itself, so nothing is over-granted. The difference is on REST: entities admitted by a guest policy can be written before the edge refusal, where MCP refuses the whole call up front. This cannot be exploited. REST should still be aligned on `currentRelationshipCapabilityContext()`.

## Suggested negative tests

- **Required follow-up, with the `batch_correct` fix.** An AAuth-admitted agent whose grant has `store` but no `correct` on type X calls `POST /entities/{id}/batch_correct` on its owner's X entity. Expect 403 `capability_denied` and no new observation. Add the same case for a protected type (`agent_grant`) without the protected capability.
- **`tenant_isolation_matrix` rows for `POST /patch_array_item` and `POST /entities/{id}/batch_correct`.** User A targets user B's `entity_id`. Expect 404, with B's observations unchanged. Today both routes have cross-user coverage only at the service layer: `tests/services/by_id_write_ownership_conflict.test.ts` covers `applyBatchCorrection`, and patch relies on the owner-scoped `getEntityWithProvenance`. `POST /corrections/transaction` already has a row.
- **REST store relationship preflight.** A store from a revoked-grant signer that carries `relationships` should be refused before any entity is written, matching MCP.
- **Conditional store across tenants.** User A sends `store` with `expected_entity_absent: true` for an identity whose derived id already belongs to user B. Assert the response has the same owner-conflict / not-absent shape as the ordinary store path, and that B's entity is unchanged.

## Residual risks

- `POST /entities/{id}/batch_correct` lacks the `correct` capability check that its three sibling routes have (Medium, same tenant, pre-existing). The Inspector Edit tab and `neotoma edit` use this route. A scoped agent with HTTP access can use it to step outside its `correct` allowlist within its owner's graph. Protected types remain gated.
- **The tenant isolation matrix could not serve as evidence in this local run.** With a temporary data directory, 6 of 19 tests failed, and all 6 were positive controls. In each, the caller could not see its own entity, fragment or observation (`GET /entities`, `/retrieve_graph_neighborhood`, `/audit_undeclared_fragments`, `/store` bulk import). The suite seeds rows directly into SQLite and calls the spawned server without an auth header, so its results depend on how that server resolves the principal. With the positive controls red, the 13 negative passes do not show isolation in this environment, including the pass on the new `/corrections/transaction` row. Cross-user refusal for the new write routes rests instead on code reading and two passing service tests:
  - `src/services/correction_transaction.test.ts` (14 tests, including foreign-graph rejection)
  - `tests/services/by_id_write_ownership_conflict.test.ts`
  
  Resolved: CI run 38585142254 (`baseline` job, release head `fdefe19e3`) ran `tests/security/tenant_isolation_matrix.test.ts` green, 19 of 19, positive controls included. The local failures came from the worktree's environment, not the code.
- The conditional-store absence check and the existing store owner-conflict envelope can tell a caller that an id it derived exists under another owner. Ids are deterministic, so this is a narrow existence signal, not a read of the data. The ordinary store path already behaved this way.
- Only agent instructions enforce the secret-file exemption for persisting bytes from agent reads. A non-compliant agent can still upload an env file or a key file as a source. That was already possible, but the new instruction pushes agents to persist file bytes more often.
- `NEOTOMA_WS_HOST=0.0.0.0` re-exposes a socket that spawns child processes without authentication. This is documented as an explicit opt-in.
- `POST /corrections/transaction` and `POST /correct` are not behind `writeRateLimit`, while `POST /patch_array_item` is. A transaction is capped at 50 entities with 50 changes each. Low.
