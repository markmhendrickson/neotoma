## Adversarial review prompt

1. **`/ready` data exposure.** Does the new unauthenticated `GET /ready` endpoint return anything beyond a boolean status and latency — entity data, row counts, table names, error internals, or anything else a public network probe should not see?
2. **`/ready` as a denial-of-service or resource-exhaustion vector.** Can an unauthenticated caller trigger expensive work by hitting `/ready` repeatedly, or does the probe bypass normal request-rate handling?
3. **`/ready` auth-bypass surface.** Does adding `/ready` to `PUBLIC_DISCOVERY_PREFIXES` (skips AAuth admission lookup) or to the pre-auth allowlist in `src/actions.ts` create a path an attacker could use to reach anything beyond the readiness handler itself — for example via path-prefix confusion (`/ready/../entities`)?
4. **Guest-principal fix correctness.** Does `RESERVED_ENTITY_PATH_SEGMENTS` correctly *narrow* guest eligibility (fewer paths get a guest principal stamped) rather than accidentally widening it, and does it fail closed (deny guest) rather than open (allow guest) for any input it doesn't explicitly recognize?
5. **Guest-principal fix collateral damage.** Does the reserved-segment check incorrectly deny guest access to a legitimate entity whose id happens to collide with a reserved word (e.g. an entity literally named `duplicates`)?
6. **Route-shadowing guard fail-open risk.** Does `assertNoShadowedRoutes()` fail *open* (boot continues silently) in any case where it should fail closed, given the PR's stated design that it no-ops when it cannot introspect Express internals?
7. **Route-shadowing guard fail-closed risk.** Conversely, could the guard incorrectly refuse to boot a legitimate, non-shadowed route table (a false positive that would turn a defensive check into an availability bug)?
8. **Manifest override legitimacy.** Does the `/ready` override in `protected_routes_manifest.json` (accepting `503` as an expected no-auth/invalid-auth status) mask a genuine auth gap, or is `503` strictly the probe's designed failure response as claimed?
9. **Fly config changes as a security surface.** Do the `fly.toml`/`fly.sandbox.toml`/`fly.operator.toml` health-check and sizing changes affect anything auth- or exposure-relevant (e.g. does pointing the health check at `/ready` change which network interface or port is checked)?

## Findings

1. **`/ready` exposes only a boolean and a latency number (concern 1).** Read `src/services/readiness.ts` in full. The response shape is `{ok: boolean, checks: {database: "ok"|"failed"}, latency_ms: number, error?: string}`. The `error` field on failure is `error.message` from the underlying query error (e.g. `"no such table: sources"` in the PR's own demonstrated failure) — a schema/table-name-shaped string, not row data, not user content, not stack traces. The probed query is `SELECT id FROM sources LIMIT 1` and only the `error` channel is consulted (`ReadinessQueryResult` interface declares only `error`, no `data` field is read or returned). Concern 1 closed: no entity data, no row counts beyond an implicit boolean "at least one query executed," no user-scoped information (the query is not filtered by `user_id`, so it proves database *reachability*, not access to any particular user's data).

2. **No resource-exhaustion vector distinct from any other unauthenticated route (concern 2).** The probe issues one indexed `SELECT ... LIMIT 1` per request, bounded by a hard timeout (`resolveReadyTimeoutMs()`, default 20s, floored at 1s). This is a cheap, single-row, indexed read — not a scan, not a write, not a join. `/ready` carries the same DoS exposure profile as `/health` (also unauthenticated, also unrated-limited in this diff) and is not a new resource-exhaustion vector beyond what already existed for any public endpoint in this deployment topology. No new rate-limiting was added or removed by this diff for either endpoint. Concern 2 closed as "no regression"; general unauthenticated-endpoint rate-limiting is a pre-existing posture question out of scope for this diff.

3. **`/ready` skip-list addition is exact-prefix, not pattern-based (concern 3).** `PUBLIC_DISCOVERY_PREFIXES` is `["/.well-known/", "/health", "/ready"]`, consumed by `isPublicDiscovery()` via `path.startsWith(prefix)` (confirmed by reading the surrounding function). Because Express normalizes and resolves the URL before handler dispatch and route matching in this codebase happens against the parsed `req.path` (not raw untrusted input), a value like `/ready/../entities` resolves to `/entities` in `req.path` before either the discovery-prefix check or route matching sees it — it does not match the `/ready` route handler itself (registered as an exact `app.get("/ready", ...)`, not a wildcard) and does not match `isPublicDiscovery()`'s `/ready` prefix as a distinct path. Confirmed by reading the `app.get("/ready", ...)` registration: it is an exact-path Express route, so Express's own router — not this diff's logic — is responsible for not matching path-traversal-shaped input, and Express's `path-to-regexp`-based matching does not treat `..` as a traversal operator here (there is no filesystem access in this handler; `req.path` is decoded and used only as a routing key, not passed to `probeReadiness` or any file/path API). No new bypass surface. Concern 3 closed.

4. **Guest-principal fix narrows, does not widen, guest eligibility (concern 4).** Read the full diff of `routeAcceptsGuestPrincipal()` in `src/actions.ts`. Before: the GET branch matched any `/entities/[^/]+(?:/(?:observations|relationships|html))?` path unconditionally — `duplicates` in that position matched and was treated as a guest-eligible entity id. After: the same regex match is followed by `return !RESERVED_ENTITY_PATH_SEGMENTS.has(match[1])` — a reserved segment now returns `false` (guest principal NOT stamped) where it previously returned `true`. Every other path shape that matched before still matches and still returns `true` (no new exclusion beyond the four reserved words). This is strictly a subtraction from the guest-eligible set, not an addition. Concern 4 closed: fails closed (deny-guest) for the four reserved words, unchanged (default allow, per prior behavior) for everything else — no widening in either direction.

5. **Reserved-word collision with a real entity id is a known, accepted, tested edge case (concern 5).** The PR body states a dedicated test asserts "an entity id merely *containing* a reserved word is still guest-readable, so the fix doesn't over-narrow." Confirmed via `tests/subscriptions/subscription_guest_auth.test.ts` — 4 new guest-principal regression cases per the PR description, including this containment case (the regex capture group `match[1]` is the *entire* path segment between `/entities/` and the next `/` or end-of-string, so `RESERVED_ENTITY_PATH_SEGMENTS.has(match[1])` is a full-segment equality check, not a substring test — `/entities/duplicates-report` would capture `"duplicates-report"`, which is not in the reserved set, and remains guest-eligible). An entity literally and exactly named `duplicates`, `merge`, `split`, or `query` (matching the full path segment) would be denied guest-principal treatment and require full auth to read via this route — a narrow, intentional, documented tradeoff stated in the PR body and code comment, not a defect. Concern 5 closed.

6. **Route-shadowing guard's no-op path is a defensive fallback, not a silent auth gap (concern 6).** Per the PR body's design note: `assertNoShadowedRoutes()` no-ops (does not fail boot) specifically when it cannot introspect Express's internal route table (`app._router.stack`, which is untyped and can shift across Express major versions) — this is a check for the *shape of a bug class* (route-ordering mistakes), not an auth check itself. Its no-op path does not disable, weaken, or bypass any of the actual auth logic in `routeAcceptsGuestPrincipal()`, `getAuthenticatedUserId()`, or the admission middleware — those remain fully active regardless of whether the shadowing guard can run. A route-shadowing bug that this guard misses would still be caught by the existing contract/integration tests that exercise the affected endpoint directly (as #2208 itself was found and confirmed via live HTTP testing, not via this guard, which postdates the bug). Concern 6 closed: the guard is additive defense-in-depth, and its absence-of-effect path degrades to "no worse than pre-#2221 behavior," not to "silently disabled auth."

7. **False-positive boot refusal is a testable, low-probability failure mode with an available escape hatch (concern 7).** The guard's positive-match logic (a static route registered after a shadowing param route) is a syntactic property of the route table, independent of request data or runtime state — it either shadows or it doesn't, deterministically, at every boot. The PR states an audit at merge time found "142 registrations, one shadowed" (the bug being fixed), meaning the guard was run against the real, current route table and produced the expected true-positive count with no unexpected trues. Should a future legitimate route addition trigger a false positive, the fix is straightforward (reorder registration, as this PR did) rather than requiring a bypass flag — consistent with the PR's stated design intent ("hard-fails rather than warns... an unreachable route table isn't a runnable state"). Concern 7 closed as a low-risk, easily-diagnosed failure mode, not a security defect.

8. **Manifest override is the documented, narrow exception it claims to be (concern 8).** Read the override entry directly (`scripts/security/protected_routes_manifest.json`): it widens accepted status codes for `/ready` specifically to `[200, 503]` for both the no-auth and invalid-auth probe cases, with a `reason` string stating `503` is `/ready`'s designed database-failure response, not an auth-rejection code, and that the route "never returns 401." Cross-checked against `src/services/readiness.ts`: the handler's only non-200 status is `503`, returned exclusively from the `catch` branch of `probeReadiness()` (database error or timeout) — there is no code path in the handler or in `probeReadiness()` that returns `401`, `403`, or any auth-shaped status, and the route itself is registered with no auth middleware (correctly, per its `requires_auth: false` manifest entry, matching its role as an infrastructure health check with no user-data return). The override does not mask an auth gap; it exists to keep `deployed_probes.sh` (G5, run post-deploy per the release skill) from misclassifying a legitimately degraded (`503`) database as a security failure. Concern 8 closed.

9. **Fly config changes affect resource sizing and check target only, not exposure (concern 9).** `git diff` of `fly.toml`, `fly.sandbox.toml`, `fly.operator.toml` shows only `[[http_service.checks]]` path/timeout/grace/interval values and `[[vm]]` memory/cpu_kind fields changed — no `[[services]]` port/protocol block, no `force_https` toggle, no new exposed port, and no change to the app's public/private network binding. Pointing the health check at `/ready` instead of `/health` changes which handler Fly polls internally for restart/routing decisions; it does not change what is reachable from the public internet (both endpoints are, and were already, public and unauthenticated by design). Concern 9 closed.

## Residual risks

- `/ready` and `/health` remain unauthenticated by design (infrastructure health checks); neither carries new rate-limiting in this diff. This matches the pre-existing posture for both routes and is not a regression, but an operator running this on a network where unauthenticated-endpoint abuse is a live concern should apply infra-level rate limiting (Fly, a reverse proxy, or similar) — out of scope for this application-layer diff.
- `/ready`'s own documented residual risk (stated in its own module comment, verified in the PR): a database file corrupted after the process already has an open handle can still return `ok` from `/ready`, since the open SQLite handle serves from its page cache. This is a known, explicitly-documented limitation of the readiness probe's design, not a security defect — it does not expose data, it under-reports a narrow class of at-rest corruption.
- The route-shadowing guard's no-op-on-introspection-failure behavior (Finding 6) means a future Express major-version upgrade that changes `app._router.stack`'s internal shape could silently stop the guard from running, with no boot-time signal that it stopped protecting anything. This is a maintainability risk worth a follow-up (e.g. a startup log line confirming the guard actually ran and how many routes it checked), not a security block for this release.
