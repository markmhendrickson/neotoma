## Findings

This release is itself a fix for a pre-existing auth bypass, not new surface being introduced — the review below evaluates whether the fix actually closes the hole and whether it opens any adjacent one.

1. **Alternate-path auth (item 1).** The vulnerable path was `validateSessionToken` (`src/services/mcp_auth.ts`), reached when a `Bearer` token matched no row in `mcp_oauth_connections`. Previously it fell through to `decodeJWTUnverified(token)` and trusted the decoded `sub`/`email` with zero signature/issuer/expiry verification — an attacker-controlled `alg:none` JWT naming any `user_id` (derivable as `sha256(email)`) authenticated as that user. The fix (`src/services/mcp_auth.ts:44-50` in the diff) removes the fallback entirely: an unresolved bearer now throws `Invalid session token` unconditionally, matching the fail-closed pattern already adopted for the Ed25519 bearer path in `0.21.4`. Concrete exploit request: `Bearer <b64url({alg:"none"})>.<b64url({sub:"<victim-uuid>"})>.x` — verified end-to-end pre-fix (returned 200 from `/me` and `/entities`); post-fix returns 401. Gate: `src/services/__tests__/mcp_oauth.test.ts` "rejects a forged unsigned JWT bearer instead of trusting its claims" test exercises exactly this request shape.
2. **Proxy trust (item 2).** Not implicated — this fix touches only the bearer-token resolution path in `mcp_auth.ts`, no `X-Forwarded-For`/`Host`/socket-address logic. No new trust surface introduced.
3. **Local-dev widening (item 3).** Not implicated — the removed fallback had no `LOCAL_DEV_USER_ID` or env-based gate at all (that absence was the bug: the comment claimed "local-only compatibility" but no local-only check existed). The fix removes the ungated fallback rather than adding a gate, which is the correct posture per the Ed25519 precedent (fail closed, don't try to scope the loophole).
4. **Unauth public route (item 4).** No new Express routes in this diff. `protected_routes_manifest.json` is unchanged; `security:manifest:check` confirms 119 routes in sync.
5. **Guest-access widening (item 5).** Not implicated — no change to `assertGuestWriteAllowed` or guest-token issuance.
6. **AAuth / agent identity downgrade (item 6).** Not implicated — this path is the MCP OAuth session-token bearer, not the AAuth signed-request path. No change to `clientInfo.name` fallback logic.
7. **Over-correction check (regression risk specific to fail-closed fixes).** Verified a legitimate, live OAuth connection token still authenticates correctly and returns the right `userId`/`email` — covered by the "still accepts a valid, live connection access token after the fail-closed fix" test in the same diff. The unused `decodeJWTUnverified` helper and its now-dead `logger` import were removed cleanly (confirmed via `tsc`/lint, no dangling references).

## Residual risks

- This is the second bearer-auth fail-closed fix in three tags (Ed25519 path in `0.21.4`, JWT path here in `0.22.1`). Both shared the same root pattern: a fallback branch trusted caller-supplied claims when a lookup failed, with a stale comment ("local-only compatibility" here, similar rationale on the Ed25519 side) that did not correspond to any actual gate. Recommend a follow-up: grep the codebase for any other `decode*Unverified` / claims-trusting fallback branches on auth paths, since this is now a confirmed recurring defect class in this codebase rather than a one-off. Filed as a residual risk, not a blocker — no other such fallback was found in this diff or in a `grep -rn "Unverified\|decodeJWT" src/` sweep at review time.
