Reviewed by reading the full `v0.27.0..HEAD` diff (20 non-merge commits, 101 files; 38 non-test, non-doc source/contract files) at head `HEAD` after merging `origin/main` (4667eac). Classifier `sensitive=true` because of two concerns: `openapi.yaml` and `src/actions.ts`. Both were walked line by line. Neither contains a new route, a changed `security:` block, a changed auth middleware, or a changed `isLocalRequest`/`forwardedForValues`.

- **openapi-security (classifier concern), `openapi.yaml`**: additive only. New schemas `ExactIdentityRead`, `PlanningDeclaration`, `SchemaRegistryCoverage`; new optional request fields `read_mode` (`/entities/query`) and `planning` (`/update_schema_incremental`, `/register_schema`); `summary=true` on `/schemas`; the `correctTransaction` `changes.minItems` 1 to 0. No `security:` block or path was added or altered. `protected_routes_manifest.json` is in sync (126 routes, 110 protected, 9 runtime-only unauth), unchanged.
- **auth-middleware (classifier concern), `src/actions.ts`**: the diff adds no `app.get/post/put/delete/all` registration. It adds (a) a pre-auth, opt-in diagnostic middleware, (b) a `morgan` skip and log-redaction helper, (c) an `exact_identity` branch inside the already-authenticated `runEntitiesQuery`, (d) a `GET /entities` 400 for `read_mode=exact_identity`, (e) `/schemas?summary=true`, (f) the `/get_entity_snapshot` visibility check, (g) `planning` pass-through. Each is covered below. The 138 `security:lint` warnings are the same 138 as in the prior review; none points at a line this release added (the `unauth-public-route` hits in `src/actions.ts` are the pre-existing `/events/stream`, `/recompute_snapshots_by_type`, `/openapi_actions.yaml` registrations).
- **Alternate-path auth (1), new exact-identity read (#2797)**: `POST /entities/query` and MCP `retrieve_entities` with `read_mode: "exact_identity"` resolve the owner only through `getAuthenticatedUserId` (HTTP) / `this.getAuthenticatedUserId()` (MCP). The executor accepts exactly three body keys, so a body `user_id` makes the request invalid (400) and is never honoured. Every SQL statement in `readBoundedIdentityInView` is bound to `owner` (`entities`, `observations`, `entity_snapshots`), identifiers are matched against `^[a-z][a-z0-9_]{0,63}$` before being interpolated into a JSON path, and the value is bound as a parameter. The route is not in `routeAcceptsGuestPrincipal` (only specific GETs and issue/subscription POSTs are), so guest tokens cannot reach it. `tests/security/exact_identity_transport.test.ts` seeds two bearer users and asserts REST, MCP, CLI and SDK proofs are owner-bound. Gate would catch: yes.
- **Existence/ambiguity oracle (exact identity)**: the response tells the owner whether one, none, or several of their own rows match, and returns their snapshot and provenance. That is information the owner can already read. `absent`/`ambiguous`/`singleton` are only returned from a pinned read view; any failure yields `unproved`, so a failure cannot be read as absence. `requested_scope.value_sha256` echoes a hash, not the value.
- **Identity values in logs (exact identity)**: handled deliberately. `morgan` skips requests whose query carries `read_mode=exact_identity`; `GET /entities` rejects the mode outright so the value is never placed in a URL; `logDebug`/`logWarn`/`logError` replace query and body with `{read_mode:"exact_identity"}`; the MCP server skips the CLI-equivalent line and replaces the result summary. REST responses carry `Cache-Control: no-store`. Residual: only the sinks named in the code were checked; any intermediary that records POST bodies (reverse proxy, APM) is outside this repo.
- **Pinned read view availability (`withPinnedReadView`)**: SELECT-only guard (`^\s*SELECT\s`, no `;`), `run`/`exec` throw, 1 s default budget (max 2 s), one pinned reader at a time, rolled back on release, reader retired on any doubt. An authenticated caller can occupy the single pinned reader and make concurrent exact-identity calls return `unproved` (and, while a pinned reader is retiring, the same for everyone). This is a bounded, fail-safe, authenticated-only availability effect, not a data exposure. Listed as a residual risk.
- **Proxy trust (2)**: no new `remoteAddress`, `X-Forwarded-For`, `Forwarded` or `Host` use. `app.set("trust proxy", true)` is unchanged. The new `createMcpLookupReceiptObserver` middleware runs before auth but only reads `req.rawHeaders` for a header the operator named via `NEOTOMA_DEBUG_MCP_LOOKUP_TRACE_HEADER` (must match `^x-[a-z0-9-]{1,55}-trace$`, so it cannot name `authorization`, `x-forwarded-for` or similar) and a title prefix; it is a no-op when either env var is unset, never alters the request, and swallows its own errors. Timing is only emitted after admission with the configured primary bearer, for one narrow `retrieve_entity_by_identifier` shape; the log line carries a client-supplied 32-hex trace id and millisecond timings, no identifier value. Not defeatable by a tunnel-shaped request because it makes no trust decision.
- **Local-dev widening (3)**: no new `LOCAL_DEV_USER_ID`, `assertExplicitlyTrusted`, `NEOTOMA_TRUST_PROD_LOOPBACK` or `NODE_ENV` shortcut in the product code. The only new env-conditional branch is the worker `__hold_for_test__` barrier, which throws unless `NODE_ENV === "test"`. The two new env vars above are diagnostics, off by default.
- **Unauth public route (4)**: no new Express routes.
- **Guest-access widening (5)**: `assertGuestWriteAllowed`, `routeAcceptsGuestPrincipal` and the guest-token issuers are untouched. Guest redaction (`redactMemberAttribution`) call sites are untouched.
- **AAuth / agent identity downgrade (6)**: none. `primaryBearerValidated` is a new local flag that only narrows when the diagnostic timing is attached (primary slot only, not the `previous` rotation slot). Agent-grant enforcement is unchanged except for the compare-only guard participants, which are stricter (next item). Note for consistency, not a regression: no read-side agent-grant check exists on `retrieve_entities`, so exact identity inherits the same read posture as ordinary entity queries.
- **Compare-only guards (#2668)**: `enforceAgentCapability("correct", ...)` covers every participant type including guard-only participants, a guard must name a declared field, must match entity type, tenant scope is enforced via `getEntityWithProvenance(..., user_id)`, and a transaction must still contain at least one real change. Cross-tenant, absent, wrong-type, undeclared and malformed guards fail closed. The added `entity_type` equality check on the current snapshot is stricter than the earlier reviewed version.
- **Current-state reads (#2792/#2798)**: replace whole-history visibility reads with lifecycle-authority-row and top-priority-row reads (`src/services/current_state_reads.ts`, `entity_queries.ts`, `entity_population_certificate.ts`, `/get_entity_snapshot`). All new SQL that selects rows is scoped by `user_id` or by ids already selected under the caller's `user_id`; recorded-cutover mode is gated by `hasRecordedEntityLifecycleCutover`, otherwise the legacy path runs. One stated trade-off: authority rows written under a foreign owner, and integrity checks of lower-priority rows, are no longer re-verified on each list/snapshot read (documented in the module header; the exhaustive checks remain for provenance, timeline, as-of reads and `verifyEntityLifecycleStorage`). For isolation this is the safer direction (a foreign-owner row cannot hide or reveal an entity); for corruption detection it is weaker on the hot path. Defence-in-depth nits, none exploitable because entity ids are owner-derived: `readDecidingObservations` and the `irregular` probe in `legacyHiddenFromDecidingRows` count or probe by `entity_id` without `user_id`; `hasLegacyFragments` is not owner-scoped and returns only a boolean.
- **Schema registry (#2772, #2803)**: registration, merge and activation run in one transaction, with refused changes rolling back and dispatching no effects. `listEntityTypesResult` now fails closed on rows whose `scope`/`user_id` combination is inconsistent with the caller, which is stricter than before. `planning` is declarative (`level`, `read_only`) and validated by a strict Zod schema on register, incremental update and catalog read; it grants no write, edit or execution authority (the tool text says so). `planning` rides the same `user_specific`/global scoping as the other schema-definition fields; no new authorization path was added. `read_only` is advisory only and could be misread by a downstream consumer as an access control.
- **CLI/setup (#2791, #2801, #2785)**: the setup transport summary now describes only entries the run wrote and no longer asserts "no network egress" (preset `c` does check the npm registry), which is a privacy-claim correction, not a widening. Claude Desktop config is relabelled. `refusalDetail` prints only the server envelope's `code` and `message` for a refused relationship write.
- **Docs/site/frontend/skills (#2780, #2773, #2788, #2778)**: `SiteMarkdownMirrorPage` takes a fixed `sourcePath` from route configuration for exact legal routes, not from user input; the splat path keeps its existing mapping. The new and changed `skills/continue-session`, `skills/status`, `skills/where`, `skills/end` content restates consent gates (no credential handling, no consent-gated send, no merge past a blocking verdict); nothing instructs an unattended outbound action.
- **CI workflow (`ci_test_lanes.yml`)**: only adds test lanes and files to existing lanes; no new secrets, triggers, permissions or third-party actions.
- **Dependencies**: `package.json`/`package-lock.json` change only the version and the `test:contract-parity` file list; no dependency added or bumped.

## Residual risks

- Exact identity reveals, to the owner only, existence and multiplicity of their own matching rows and returns their snapshot. No cross-tenant path found.
- Pinned reader contention: an authenticated caller can cause other callers' exact-identity reads to report `unproved` for up to the 1 s budget. Fail-safe, not an exposure.
- Identity values in a non-repo intermediary's POST body logs (reverse proxy, APM) are outside this review.
- Current-state reads no longer re-verify foreign-owner authority rows and lower-priority observation integrity on each read; corruption of that kind surfaces only on the exhaustive paths.
- `planning.read_only` is declarative; consumers must not treat it as authorization.
- `npm run test:security:auth-matrix` needs `npm run build:server` first (global setup refuses without `dist/`) and an isolated data dir; environment-only, not a product risk.
- No AI-provider review was run (`NEOTOMA_AI_REVIEW_PROVIDER=none`); this review is a manual read by the preparing agent. Operator approval of the verdict is still pending.
