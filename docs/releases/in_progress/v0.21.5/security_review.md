## Findings

1. **Alternate-path auth / guest-access widening (`src/actions.ts`, `GET /entities/:id/html`).** The route branches on `resolveRoutePrincipal(req, ["user", "guest"])` — unchanged by this diff. Authenticated reads are scoped via `.eq("user_id", userId)`; guest reads go through `resolveGuestScopedEntityAccess` (also unchanged). The new CSP/`X-Content-Type-Options` headers are set unconditionally after both branches resolve, before `res.send(html)`, so the mitigation covers both paths identically. No new route, no widened guest surface. Covered by `tests/security/rendered_page_csp.test.ts`.
2. **Stored XSS via `html_body` — the vulnerability the fix addresses (GHSA-qp63-9r52-4q25, referenced by commit message).** `html_body` is author-supplied free text on a `rendered_page` entity snapshot, served verbatim. The global CSP (set elsewhere for the authenticated app shell) allows `'unsafe-inline'`, so an injected `<script>` in `html_body` would execute in the response's origin, reachable via guest `access_token` links. Fix: a route-local CSP override (`script-src 'none'`, `default-src 'none'`, `sandbox allow-same-origin`) scoped to only this response, leaving the global CSP untouched for other routes. `X-Content-Type-Options: nosniff` closes the sniffing variant. Verified by reading the diff hunk directly: the header assignment sits between the guest/user branch resolution and `res.send(html)`, applies unconditionally. Regression test `tests/security/rendered_page_csp.test.ts` stores a `rendered_page` with a script payload in `html_body` and asserts both headers on the live response — ran directly, passes.
3. **Envelope key-derivation cleanup (`src/crypto/envelope.ts`).** Prior implementation transmitted `encryptedKey` via an unauthenticated XOR wrap of the AES-GCM content key against the raw ECDH shared secret (comment: "simple XOR for now"). Both parties can already derive the same key from the shared secret via HKDF, so the wrap was redundant, not a standalone confidentiality mechanism — but it did add exposed key material and a non-AEAD operation to the wire format. Fix: derive the key via HKDF-SHA256, salt bound to the per-envelope ephemeral public key (previously empty salt), and mark the derived `CryptoKey` non-extractable (`extractable: false`). `encryptedKey` is retained as `new Uint8Array(0)` only for wire-shape compatibility. Note on reachability: `encryptResponseMiddleware` is mounted and `req.publicKey` is populated on the fully-verified Ed25519-bearer path (signature-gated, post the GHSA-33x4 fix) — this is a narrow, signature-gated surface, not literally dead code, but no first-party client provisions this path today. Covered by `src/crypto/crypto.test.ts`, which asserts `encryptedKey.byteLength === 0` so a reintroduced wrapped-key path fails the test.
4. **Proxy trust / local-dev widening.** No changes to `isLocalRequest`, `forwardedForValues`, `LOCAL_DEV_USER_ID`, or any proxy-trust helper. `auth_topology_matrix.test.ts` (18 passed, 1 skipped) confirms no regression.
5. **Unauth public route.** No new Express routes. `security:manifest:check` reports 118 routes in sync with `openapi.yaml`, zero drift.
6. **[FIXED DURING THIS REVIEW] Concurrency race in the standing-rules failure signal (`src/services/standing_rules.ts`).** The merged commit (`78dbcbef`, PR #2131/#2133) originally carried its "did the lookup fail" signal on a module-level `let lastLookupFailure` variable: reset to `null` at the start of `getActiveStandingRules`, set on error/exception, and read back by `getActiveStandingRulesResult` after `await`ing the call. Because `getActiveStandingRules` is invoked once per MCP `initialize` for the requesting user, and MCP sessions for different users run concurrently on the same server process, two overlapping calls can interleave across the `await` boundary: call A resets to `null` and suspends on its DB round-trip; call B (a different user) resets to `null` again, and if B's own outcome (success or failure) resolves and is read before A's continuation resumes, A's later-arriving outcome can overwrite or be overwritten by B's — producing a false `lookup_failed` for a healthy lookup, or worse, masking a genuine failure as success. This is the exact regression class (#2131) the surrounding fix was written to close, reintroduced by a different mechanism. **This was found and fixed during release preparation, before this release shipped**: `lookupActiveStandingRules()` now returns `{ rules, lookup_failed, error? }` directly from each call — no shared module state — and both `getActiveStandingRules` and `getActiveStandingRulesResult` derive from that one per-call result. Added regression test `tests/unit/standing_rules.test.ts` › "keeps concurrent lookups for different users independent under adversarial interleaving": uses deferred promises to force a resolution order where a healthy call's continuation is paused across a failing call's write, and asserts the healthy call's own outcome is unaffected. Verified this test fails against the pre-fix module-state implementation (reproduced by temporarily reverting the source) and passes against the fix.
7. **AAuth / agent identity downgrade.** Not applicable — no auth-tier code touched. The standing-rules and server.ts changes are read-path (session-init payload enrichment), not write-path auth gating.
