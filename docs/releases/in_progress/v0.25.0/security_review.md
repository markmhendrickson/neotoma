## Findings

Range `v0.24.0..HEAD` is four changes: #2523 (skill retirement), #2541 (capability manifest), #2539 (issue sync `repo`, allowlist, dry run) and #2446 (schema write scope, migration truthfulness, `force`). The classifier flags three concerns, one per sensitive area touched.

- **openapi-security (`openapi.yaml`).** The diff adds request and response fields and 400 and 403 responses to `POST /issues/sync`, and adds `force` and the `migration_result` / `scope` / `user_id` response fields to the schema routes. No `security:` block, no route and no auth requirement changed. `security:manifest:check` is in sync at 123 routes, and `openapi:bc-diff` reports no breaking changes and eight non-breaking additions. No finding.
- **auth-middleware (`src/actions.ts`).** The changes are inside the existing `handleIssuesSyncHttp` and `POST /update_schema_incremental` handlers. Neither touches `isLocalRequest`, `forwardedForValues`, the auth middleware order or any guest policy. Both routes keep the authenticated principal the same way as before. The schema route now always passes the authenticated `userId` to the service (before, it passed it only when `user_specific` was true), which makes the service resolve within the caller's own scope, never another principal's. No finding.
- **root-landing (`src/services/root_landing/site_nav.ts:86-90`).** Two static nav entries are removed. No handler, request or header logic. No finding.
- **1. Alternate-path auth.** No new path reaches a privileged surface. MCP `sync_issues` and REST `POST /issues/sync` enforce the same allowlist in the shared service (`resolveSyncTarget` in `src/services/issues/sync_issues_from_github.ts`), so neither transport is a bypass. The same check guards `syncIssueIfStale`. The Inspector bulk close and remove path resolves each row's repo through `resolveIssueRepo` and does not call GitHub for a repo outside the allowlist. `src/server.ts` changes the `initialize` skill list and passes `force`; it does not change who can call either.
- **2. Proxy trust.** No new reads of `X-Forwarded-For`, `Forwarded`, `Host` or `req.socket.remoteAddress`. `security:lint`: 0 errors, 136 warnings, the same count as at v0.24.0.
- **3. Local-dev widening.** No new reference to `LOCAL_DEV_USER_ID`, `assertExplicitlyTrusted` or `NEOTOMA_TRUST_PROD_LOOPBACK`. The one new environment variable, `NEOTOMA_ISSUES_ALLOWED_REPOS`, only narrows or widens which repos the server's GitHub credential may touch, and unset means the configured repo only.
- **4. Unauth public route.** No new Express routes. The manifest check is in sync.
- **5. Guest-access policy widening.** `assertGuestWriteAllowed`, `routeAcceptsGuestPrincipal` and the guest-token issuers are untouched.
- **6. AAuth / agent identity downgrade.** No AAuth, grant or attribution code changed.
- **Issue-sync repo allowlist (new authorization control).** The server's GitHub credential is instance-level, so a caller-supplied `repo` is an authorization decision. `resolveSyncTarget` validates the slug with `isValidRepoSlug` (`src/shared/repo_slug.ts`), then calls `assertRepoAllowed` before any GitHub or local access, for pull, push and dry run. Matching is exact and case-insensitive, with no wildcards. A malformed allowlist entry is dropped, never widened. With nothing configured only the configured repo passes (fail closed). The 403 text is identical whether or not the repo exists and does not echo the repo or the list, so the endpoint is not a repo-existence oracle. Reverting the check turns 13 service tests red (per the PR's revert-to-red table).
- **Push default.** `push` defaults to true only for the configured repo, so pointing a sync at another allowlisted repo cannot export local public issues there unless the caller passes `push: true`. Reverting that default turns 2 tests red.
- **Residual: allowlisting a repo also permits comments and closes there.** Documented in the supplement and in `docs/subsystems/issues.md`. It is an operator decision made by editing server configuration.
- **Residual: `submit_issue` `target_repo` is not gated by the allowlist (#2540).** Pre-existing; this release does not widen it, and it now stops sending follow-ups for such rows to the configured repo.
- **Residual: a stored row repo that is present but malformed falls back to the configured repo (#2542), and the `issue_number` lookup is not repo-scoped (#2543).** Both are non-blocking follow-ups filed by the PR review.
- **Schema scope (`src/services/schema_registry.ts`).** `activate()` selects the caller's own user-scoped row, else a global row, else throws, and then targets every later query by row id. A version-string collision can no longer reactivate another principal's private row or a sibling scope. `user_specific: false` reads only the global row and returns `ERR_SCHEMA_SCOPE_MISMATCH` when none exists, so an explicit global write cannot silently copy a caller's private override into the global schema. `migrate_existing` is scoped to the authenticated caller through `migrate_user_id`. Covered by `tests/integration/update_schema_incremental_scope_mismatch.test.ts` and `update_schema_incremental_defect_cluster.test.ts` (14 tests through the real handlers and HTTP routes).
- **Local filesystem write (non-auth, from #2523).** `src/cli/skills_mirror.ts` calls `unlinkSync(targetDir)` on a harness skills directory only when `isSymlinkTo(targetDir, sourceDir)` confirms it is Neotoma's own whole-directory symlink. It removes the link itself and never its target. Foreign per-skill content is left alone. Covered in `tests/cli/skills_mirror.test.ts`.

## Suggested negative tests

The allowlist rejection, the malformed-slug rejection, the push default, the scope-mismatch error and the version-collision case each have a test that was confirmed red against the reverted change. `tests/security/auth_topology_matrix.test.ts` passes on the release head (18 passed, 1 skipped).

## Residual risks

- Allowlist scope is a server-wide operator setting, not per caller. Any authenticated caller can sync any repo the operator listed. This is the intended model for an instance-level credential.
- `isDeprecatedSkillDir` fails open (a malformed `SKILL.md` counts as not deprecated). The cost is that a retired skill is advertised. It is not a security exposure.
- The default write scope for `update_schema_incremental` changed (see the supplement's Breaking changes). This is a correctness change, not an exposure: the new scope is always the caller's own.
