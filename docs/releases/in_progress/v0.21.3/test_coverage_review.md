## Surface: `/.well-known/oauth-protected-resource[/mcp]` returns 200 unauthenticated (was 401)

**Classification: Covers user-observable behavior end-to-end.**

`tests/integration/wellknown_discovery_unauthenticated.test.ts` boots a real Express app instance (`app.listen(0)`), issues real HTTP `fetch()` requests with no `Authorization` and no `X-Connection-Id` header (the exact shape a first-time MCP client sends), and asserts on the actual response status and body — including that the `resource` field is populated and `authorization_servers` is non-empty, not just a bare 200. This is the real regression: a 200 with an empty body would be equally useless to a bootstrapping client, and the test explicitly guards against a soft "not 401" assertion.

## Surface: `/.well-known/openid-configuration` returns explicit 404 (was implicit 401 via catch-all)

**Classification: Covers user-observable behavior end-to-end.**

Same test file pins this route to exactly 404, not `!== 401`. This distinguishes "explicitly not offered" from a synthetic 200 (which the architecture decision in the commit message explicitly rejects) and from the old catch-all 401 (which reproduced the #2049 dead-end on a sibling path).

## Surface: `WWW-Authenticate` chain resolution from `/mcp`

**Classification: Covers user-observable behavior end-to-end.**

The test follows `/mcp`'s own `WWW-Authenticate` header to whatever URL it advertises and asserts that URL resolves without a second 401 — directly reproducing the deadlock chain described in the bug report (401 → follow header → 401 again → no way out).
